## Project in one paragraph

Testing whether LLMs can rapidly prototype MAPE control-loop modules (Monitor → Analyser → Planner → Executor) that compose into functional autonomous controllers in CloudSim 7.x. Three module families are built and independently validated: QoS/load-balancing (VM migration), throughput (cloudlet migration), and power (VM migration for energy). GUID self-labelling is the composability mechanism under test; the standing headline finding is that GUID compatibility does not predict controller quality (three families running), while GUID-agnostic modules that re-derive their own signals keep winning.

## Phase Transition — Feasibility Testing Complete, Realistic Stress-Testing Begins (2026-07-17)

**Explicit reframing of project purpose, stated directly by the project owner.** Every result validated to date across all three families (QoS 90.2%, throughput ~69%, power 43.1%±4.1) answered the feasibility question — can LLM-generated modules compose into functional, positive-effect controllers — which is treated as closed (also see the 2026-07-09 "Meeting Outcome — Direction Set" entry above, which already marked this transition once at the direction level). Current goal is different in kind, not degree: build the most realistic scenario achievable and use it to properly stress-test the controller library, rather than continue optimizing for comparability with the feasibility-phase numbers.

**Consequence: two previously-conflated cautions now pull apart, and only one still applies.** Continuity with prior baselines (old absolute cost/energy/makespan figures) is no longer a constraint — it's expected and acceptable for the realistic-scenario work to produce non-comparable numbers to every feasibility-phase result, including this session's own RAM/BW-rescale and random-allocation baselines. What still applies: changing one scenario axis at a time, so that once the realistic scenario is fully assembled, it's still possible to attribute any controller behaviour (including regressions) to a specific realism dimension rather than an undifferentiated pile of simultaneous changes. This is why VM/cloudlet core count randomisation and the cloudlet-length distribution change (both previously deferred specifically to protect feasibility-phase comparability) are now in scope, while the "one axis at a time, isolated" build discipline itself is retained rather than dropped.

Previously deferred as too foundational to touch casually (every historical result depends on it); **now in scope** given the phase transition — **not yet done, next concrete step**.
- Cloudlet file/output size — **done**: log-normal (median ≈20MB, σ≈1.3), independent of cloudlet length and of each other (separate seeds), matching the heavy-tailed-not-uniform reasoning used for cloudlet length. **Ground-truth utilization extended in four directions, closing a real asymmetry: RAM/BW had avg+peak utilization tracked, MIPS only had absolute headroom (free MIPS), no normalized percentage.**
- **Host MIPS utilization (avg+peak)** added to what's now named `updateHostResourceUtilizationGroundTruth` (renamed by the project owner from `updateResourceUtilizationGroundTruth` mid-session), using `vm.getTotalMips()` — caught before it shipped that `vm.getMips()` is a per-PE rate, not the VM's total footprint (confirmed from this project's own `requestPeAllocation`/`requestPeDeallocation`, which already treat `vm.getMips()` as a per-PE share, and `getVmEffectiveThroughput`, which multiplies it by a PE count to get an aggregate); using it directly would have undercounted every VM with more than one PE.
- **VM-level MIPS utilization (avg+peak)** added as a new signal with no existing counterpart — `updateVmCapacityGroundTruth` already tracks VM-level headroom but nothing measured "is this individual VM's own allocation over- or under-used relative to its actual workload" the way host-level utilization measures the same question for the fleet. Computed from `peDemand / vm.getNumberOfPes()`, the same ratio `updateVmCapacityGroundTruth` already derives internally for headroom, just not previously exposed as a percentage. Two bugs caught in the project owner's first draft before it shipped: writing the result into `vmFreeMipsSum` (the pre-existing headroom accumulator, which would have silently corrupted `getAvgVmFreeMips()`) instead of a new field, and computing an absolute MIPS-used quantity (`peDemand * vm.getMips()`) rather than a normalized 0–1 ratio. - **Explicitly decided not to add VM-level RAM/BW utilization**, unlike MIPS. VM RAM/BW allocation is set directly by `requestRamScaling`/`requestBwScaling` with no separate per-cloudlet consumption signal the way `peDemand` exists for MIPS (confirmed by inspection, not exhaustively source-verified) — a VM RAM/BW "utilization" metric would read 100% by construction, allocation being demand by definition in this model, not a genuinely new signal.
- **Host-level and VM-level utilization variance added** (`updateHostUtilizationVarianceGroundTruth` — RAM/BW/MIPS together in one pass, `updateVmUtilizationVarianceGroundTruth` — MIPS only, matching the host/VM split decided above), same shape as the pre-existing `updateDemandVarianceGroundTruth`. **Headroom variance was explicitly not built as a separate metric** — for any resource, headroom-ratio and utilization-ratio are complements (`h = 1-u`) and variance is invariant under that transform (`Var(1-u) = Var(u)`), so a separate headroom-variance metric would be mathematically identical to the utilization-variance already built, not new information. **Flagged, not resolved: the new host-level variance method excludes dead/failed/powered-down hosts (matching `updateDemandVarianceGroundTruth`'s existing precedent — an evacuated host reads as 0% utilized, an artifact not real spread), but its avg/peak sibling (`updateHostResourceUtilizationGroundTruth`) does not have this exclusion and never has.** The two methods now describe slightly different host populations for the same underlying metric family; not yet reconciled either direction.
- **Separately, whether demand-variance (`updateDemandVarianceGroundTruth`, uses `vm.getCurrentRequestedTotalMips()` — actual current workload demand) and the new MIPS-utilization-variance (uses `vm.getTotalMips()` — allocated/rated capacity) are meant to be two distinct signals or the same thing measured twice was raised and left an open decision, not resolved this session.**

**Host storage headroom/utilization/variance added, extending storage from a single admission-check call site (`canMigrateGuestToHost`) to full parity with MIPS/RAM/BW — see 06-cloudsim-notes.md, "Host Storage — `getStorage()` Is Almost Certainly a Depleting Pool, Not a Capacity Getter," for the full finding.** One-line summary: `host.getStorage()` is inferred (not source-confirmed — no CloudSim library source has ever been available in this project folder) to be a depleting/available pool like the other three resources' `getAvailableX()` calls, not a total-capacity getter; there's no paired `getTotalStorage()`. Total is derived as `used + getStorage()` rather than divided against `getStorage()` directly. **Flagged for empirical verification before trusting any `avg_storage_util`/`peak_storage_util`/`avg_host_storage_util_variance` figure**: log `host.getStorage()` immediately before/after a VM lands on a host — if it drops by exactly `vm.getSize()`, the inference holds; if not, every storage-utilization formula needs flipping. Woven into the same three existing multi-resource methods (utilization, headroom, variance) as a fourth resource alongside MIPS/RAM/BW, rather than three new standalone methods, matching the project's own established organization (group by concept, not by resource).

## Current state (2026-08-04) — two more harness bugs found and fixed continuing the seed-42 clean-baseline rerun, deadlocks down from 91 to 32, `executor_v1`/`sendCloudlet` slated for retirement

**Continuing directly from 2026-08-03's precondition (clean compatibility/crash logs before spec review resumes) — two more root causes found and fixed, both confirmed via full reseep, not just designed.**

**Sixth catalogued GUID-mismatch mechanism: `executor_v1`'s `sendCloudlet` misdirecting an unchecked raw `datacenterId` straight into `CloudSimShutdown`, silently ending the entire simulation with no exception.** `Selector.sendCloudlet`'s original guard was a numeric bounds check (`datacenterId < 0 || datacenterId >= CloudSim.getNumEntities()`) rather than an identity check — any in-range-but-wrong id, including CloudSim's own `CloudSimShutdown` entity (id 0, created via `CloudSim.init(numUser=1, ...)`), passed straight through. `CloudSimShutdown` calls `CloudSim.abruptallyTerminate()` the instant it receives its `numUser`-th event; with `numUser=1` in this harness, one misdirected event ends the whole run. Traced from symptom to CloudSim-engine root cause via unconditional CHECKPOINT-print instrumentation in `mapeCycle()` (showing `schedule()` for the next tick succeeding yet the tick never firing) plus direct source reads of `CloudSim.run()`/`runClockTick()`'s `abruptTerminate` check and `CloudSimShutdown.java` itself, then confirmed directly with a one-off `CloudSim.getEntityName(datacenterId)` print showing the actual target. ## Current state (2026-07-29), continued further — full Planner/Analyser library reviewed for self-imposed resilience floors: none found, and the gap looks structural (declared-goal scoping) rather than a sampling artefact

## Current state (2026-07-30) — a fourth GUID-mismatch mechanism found (cloudlet double-counting, not just destruction/misdirection), a new seed-normalised recovery metric built and shown to inherit the same vulnerability, and the recurring control-character corruption bug finally closed for good

**Confirmed, via a back-calculated "implied completed count" and one mathematically impossible reading, that `planner_v4`+`executor_v1` (GUID-incompatible) double-counts completed cloudlets rather than genuinely completing more work.** `executor_v1`'s `sendCloudlet` misreads `planner_v4`'s 3-element vm-creation payload (`{topTier, topTier, datacenterId}`) as `{cloudletId, datacenterId}`, so it re-dispatches an already-existing (often already-finished) cloudlet instead of creating a VM (see the earlier 2026-07-29 continuation entry that first identified this pairing as a payload mismatch). Solving `completed = completion_rate × other / (1 − completion_rate)` per seed and comparing against baseline's own implied count surfaced seed 44 reading **`completion_rate = 1.7179`** for the controller row — a value mathematically impossible for a true bounded ratio, meaning the numerator (`newList.size()`, i.e. `getCloudletReceivedList().size()`) exceeded what should be structurally possible. Mechanism: `getCloudletReceivedList()` is a plain `List`, not a `Set`, with no cloudlet-id-based deduplication anywhere in the return path — resubmitting an already-processed cloudlet lets it be appended a second time on its next return. Confirmed corroborating pattern across all 10 seeds: divergence from baseline tracks `actions_executed` almost exactly (seeds with 0–1 mismatched actions read identical to baseline; the 72- and 339-action seeds show the largest, and in one case impossible, inflation). Retroactively corrects the earlier "controllable cost vs completion rate" chart interpretation from this session's Excel work — the high-cost/high-completion-rate cluster on that chart is this artifact, not a genuine pay-more-complete-more capacity tradeoff.

**Open, not yet source-confirmed: whether cost metrics are contaminated the same way.** If `controllable_cost`/`total_cost` are accrued in the same `processCloudletReturn` code path as the list-append (plausible but not verified this session), they would double-bill on the same resubmitted cloudlets for the same reason `completion_rate` double-counts them. `avg_power`/`total_energy` are structurally safe from this specific mechanism (integrated from host/VM power draw over time, not from cloudlet counting); makespan is likely also safe (a duplicate list entry doesn't move the last-finish-time) but this hasn't been verified against what happens if a resubmitted cloudlet is assigned a new finish time. Flagged as the concrete next code-read, not yet done.

**New seed-normalised metric built, `completion_rate_recovery_pct`, added to `AverageByController.java`'s output.** Answers a different question than the existing gate: not "did the controller regress vs. baseline" (the gate's job) but "how much of baseline's own shortfall did the controller recover." Formula: `(controller_completion_rate − baseline_completion_rate) / (1 − baseline_completion_rate) × 100`, computed per seed before averaging — deliberately *not* a blanket comparison against a universal 1.0 ceiling, since baseline < 1.0 in a given seed is usually genuine unavoidable seed-level loss (a host permanently died and its cloudlets couldn't all be evacuated in time), not something any controller could fix; grading every seed against 1.0 would reintroduce exactly the seed-difficulty confound the existing % change methodology already exists to avoid. 0% = no different from baseline, 100% = recovered every cloudlet baseline lost, negative% = made it worse, blank/undefined when baseline was already exactly 1.0 (nothing to recover). **Not yet ported to `average_by_controller.py`** — the two tools are meant to stay cross-validated twins; this is now a known parity gap, not an oversight to repeat silently.

**Re-run on the 10-seed dataset: the established winner cross-checks cleanly, but the new metric itself inherits the cloning vulnerability above when used unfiltered.** `planner_v9`+`executor_v8` (`analyser_v7`, `monitor_v6/7/8/9`) still shows makespan +3.2%, power −21.6%, 10/10 seeds passing the gate — now also `completion_rate_recovery_pct ≈ +11.25%`, consistent with the rest of its record. But sorting the full 10,000-row table by this metric unfiltered puts `planner_v4`+`executor_v1`-family mismatches at the entire top of the leaderboard — every one `guid_compatible=False`, `seeds_passing_gate=0`, the single highest value in the dataset (+84%) paired with power getting **worse** (+20%), not better. The recovery metric is built directly from `completion_rate`, so it inherits that metric's exact vulnerability to the cloning artifact — it must be read through the existing validity gate the same way every other metric in this project has needed to be, not ranked on directly. New standing rule, same shape as the existing "never trust an ungated number" convention: **never rank on `completion_rate_recovery_pct` without filtering by `guid_compatible`/`seeds_passing_gate` first.**

**A −432% recovery reading, initially alarming-looking, resolved to the already-known `planner_v6`/`planner_v7`+`executor_v3` total-VM-pool-destruction mismatch, not a new failure mode.** That combo's `completion_rate_mean = 0.0` across all 10 seeds (every cloudlet lost, every seed) — the extreme magnitude (rather than a cleaner −100%) comes from the recovery formula's per-seed denominator (`1 − baseline`): in seeds where baseline's own completion rate happened to be very close to 1.0, that denominator is tiny, so collapsing to 0% divides by almost nothing and the percentage blows up into the hundreds for that seed before being averaged in with the rest (std 513 on that row, confirming wildly different-sized denominators across seeds, not a calculation error).

**The recurring embedded-control-character corruption (first hit and fixed 2026-07-29 building `AverageByController.java`) resurfaced twice more this session and is now closed for good by removing the mechanism, not patching another instance of it.** Every attempt to write the literal six-character Java escape for a SOH control character as source text — via `Edit`, via `Write`, via a `bash`/Python heredoc — was silently converted into the actual raw control byte by the tooling itself before landing in the file, reproducing the identical bug three separate times despite two of those attempts being the fix for the previous occurrence. Root-caused as a property of the escape sequence itself, not any one tool: switched the grouping-key delimiter from a string-literal escape to a delimiter built at runtime, `monitor + (char) 1 + analyser + (char) 1 + planner + (char) 1 + executor` — since `(char) 1` is ordinary Java source text with no special encoding for anything in the pipeline to mis-render, this closes the whole bug class rather than the one instance of it. Confirmed clean via `grep -P '[\x01-\x08\x0e-\x1f]'` after the fix.
