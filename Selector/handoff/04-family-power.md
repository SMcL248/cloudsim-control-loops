# 04 — Power Family (VM Migration for Energy)

_Architecture & GUID rules: 01-architecture.md. CloudSim power-package bugs: 06-cloudsim-notes.md and 07-limitations.md._

## Power-Aware Family — Third Control Loop (Exploration, 2026-07-03)

### Rationale

Third of the three originally-named candidate systems goals (see Cloudlet Migration Family Rationale above): minimise power/energy use via VM migration. Chosen as the next family to explore after cloudlet migration reached a validated state. Distinct from the other two families in one important way: it reuses VM migration's existing action mechanism (`requestVmMigration` already exists, no new `ActionSpace` method needed, unlike cloudlet migration's `moveCloudlet`) — the novelty is entirely in the metering (power, not variance or makespan) and in the Planner's objective (drive hosts to complete emptiness, not balance or speed).

### Infrastructure: CloudSim's Power Package

`org.cloudbus.cloudsim.power` (+ `.power.models`, `.power.lists`) provides `PowerHost`/`PowerVm`/`PowerDatacenter` as drop-in extensions of the base `Host`/`Vm`/`Datacenter` classes, plus `PowerModel` implementations (`PowerModelLinear`/`Square`/`Cubic`/`Sqrt` — generic curve shapes — and `PowerModelSpecPower*` — real SPECpower-benchmarked hardware profiles). `PowerHost.getPower()` reads current draw; `PowerDatacenter.getPower()` (a plain public getter, not to be confused with the host-level method of the same name) accumulates **total energy for the whole run in Watt-seconds (Joules)**, computed automatically every processing cycle via `host.getEnergyLinearInterpolation(fromUtilization, toUtilization, timeDiff)` — no custom instrumentation needed for the top-line energy figure at all, unlike the demand-variance and makespan ground truths in the other two families, which are hand-computed.

**CloudSim 3.0 docs ≠ CloudSim 7.0.1 behaviour — confirmed by direct source inspection, not assumed.** This project runs CloudSim 7.x (confirmed: `HollowedControl` already imports `org.cloudbus.cloudsim.core.HostEntity`/`GuestEntity`, an entity-abstraction layer that does not exist in 3.0). Verified differences against the `7.0` tag on `Cloudslab/cloudsim`: `PowerHost` now `implements PowerHostEntity extends HostEntity` (interface layer new in 7.0); `getPower(double)` is `public` in 7.0, `protected` in 3.0; `getMaxPower()`/`getEnergyLinearInterpolation()` still exist and compute the same formula but are now **default methods on the `PowerHostEntity` interface**, not concrete methods on `PowerHost` itself; CloudSim 7.0 also added nested-container simulation support (`PowerGuestEntity`, `getMigrableContainers()`), irrelevant to this project but evidence of a substantial refactor lineage ("CloudSim 7G"), not a patch release. Lesson: verify against the actual pinned source before citing CloudSim API specifics — search results default to 3.0-era (2012) javadoc.

### Architecture Decision: No New Interfaces Needed

Initial instinct was to create parallel types (`PowerHollowedControl`, Power-specific `Monitor`/`ActionSpace` variants) to accommodate `PowerGuestEntity`/`PowerHostEntity`. **Confirmed unnecessary by reading the actual current `HollowedControl.java`**: every method in it (`requestVmMigration(GuestEntity, HostEntity)`, `getVmList(): List<GuestEntity>`, `getAllHosts(): List<HostEntity>`, `updateGroundTruth()`'s internals) is written exclusively against the base entity interfaces — never a concrete `Host`/`Vm`/`Datacenter` type. Since `PowerHost`/`PowerVm` already satisfy `HostEntity`/`GuestEntity` via the `PowerHostEntity`/`PowerGuestEntity` interface chain, they flow through the existing, unmodified `HollowedControl<M,D,A>` with zero changes required. Confirmed empirically, not just architecturally: `HollowedControl` running cloudlet-migration's own `monitor_v1`/`analyser_v1`/`planner_v1`/`executor_v1` against a `PowerHost`-backed scenario compiled and ran correctly with no modifications to the framework class.

**Root cause of the compile error that prompted the investigation** (`requestVmMigration(PowerGuestEntity, PowerHostEntity)` "must override or implement a supertype method"): Java requires *exact* parameter type matches for `@Override` — parameter types are invariant, unlike covariant return types. Narrowing `GuestEntity`/`HostEntity` to `PowerGuestEntity`/`PowerHostEntity` in a subclass creates an unrelated overload, not an override. Correct pattern (matching the project's own established `instantiate()`-style single-chokepoint philosophy): keep the override signature identical to the interface, downcast internally in the method body only where Power-specific behaviour is actually needed.

**General principle for the rest of this family's development:** the entity abstraction layer exists specifically so code written against `HostEntity`/`GuestEntity` keeps working when the concrete backing type changes. Default assumption should be "the existing interface already covers this," not "I need a parallel type" — every instance of the latter instinct so far (interfaces, `PowerHollowedControl`) turned out to be unnecessary.

### Ground Truth: Empty Host = 0W (Decided) and Two Library Bugs Found

**Decision: an empty (0-VM) host counts as powered off (0W), not idle-but-on.** Standard assumption in VM-consolidation literature (Beloglazov & Buyya and follow-on work) and makes the objective directly sensitive to consolidation. Turns out to be **built into `PowerModelLinear.getPower()` already** — it has an explicit `if (utilization == 0) return 0` branch, independent of `staticPowerPercent` — so no custom ground-truth code was needed to implement this decision at all.

**`HollowedControl.updateGroundTruth()`/`getGroundTruthAvgVariance()` is VM-migration-specific and hardcoded into the shared framework class — not applicable here.** Same root cause as why `average_cpu_demand_variance` went dead for cloudlet migration: it's one fixed calculation (host-level demand-pressure variance) baked directly into `HollowedControl`, not parameterised per family. For the power family this is simply ignored; the real ground truth is `PowerDatacenter.getPower()`, read externally after `CloudSim.stopSimulation()` — which accumulates correctly regardless of what `HollowedControl`'s internals do, since `PowerDatacenter` computes it independently every processing cycle.

**Bug 1 — `PowerDatacenter` scheduling interval of 0 causes an infinite zero-delay self-rescheduling loop.** `PowerDatacenter.updateCloudletProcessing()` re-enters its own "cancel and reschedule" branch whenever `cloudletSubmitted == CloudSim.clock()`; with `schedulingInterval=0`, each reschedule lands at the identical simulated timestamp, so the clock never advances past the moment cloudlets were submitted and the real per-cycle processing logic (energy accounting, `checkCloudletCompletion()`) is never reached. Symptom: simulation runs forever (alive, producing no further output) after the "Sending Cloudlet" log lines, must be killed manually. **Fixed**: use a small positive `schedulingInterval` (1) instead of 0.

**Bug 2 — CloudSim 7.0 library bug in `HostDynamicWorkload.getCompletedVms()`.** Confirmed by direct source inspection:
```java
public List<GuestEntity> getCompletedVms() {
    ...
    if (guest.getCurrentRequestedTotalMips() == 0) { vmsToRemove.add(guest); }
    if (guest instanceof VirtualEntity vm && vm.getNumberOfGuests()==0) { vmsToRemove.add(vm); }
    ...
}
```
The second condition — added for CloudSim 7.0's nested-container support — checks "does this VM have zero nested containers," which is unconditionally true for any ordinary VM (this project never uses nested containers), independent of whether its cloudlets have actually finished. Result: **every VM gets flagged for removal after the very first processing cycle**, regardless of real remaining cloudlet length — observed as all 12 VMs deallocating at t=1.01 while cloudlets (needing thousands of time units) had barely started. This is a genuine library regression, not fixable from calling code directly. **Fixed** via a narrow subclass (`FixedPowerHost extends PowerHost`) overriding only `getCompletedVms()` to drop the erroneous second condition, keeping the (correct) MIPS-demand check. Documented as a CloudSim-7.0-specific gotcha in Known Limitations below, in the same category as the earlier `getMips()` per-PE-vs-total trap.

Both bugs are now fixed; a no-migration baseline run completes correctly end-to-end (utilization stable and realistic across ~6115+ time units, matching the historical cloudlet-migration makespan for this scenario).

### Power Model Calibration

Initial parameterisation (`PowerModelLinear(10, 0)`) was a naive placeholder — `maxPower=10` has no real-world grounding, and `staticPowerPercent=0` removes the idle/static power floor entirely, which removes most of the reason consolidation saves energy in the classic literature (the whole argument rests on hosts carrying a large fixed cost just for being on — typically 60–70% of max power at idle — which is what makes packing VMs onto fewer hosts an actual win rather than a wash). **Recalibrated to `PowerModelLinear(250, 0.6)`**: 250W max power (plausible real-server range, matching the SPECpower-derived hardware profiles the CloudSim power package is built around) and 60% static-power fraction (150W idle floor), giving the objective a continuous gradient toward consolidation rather than an all-or-nothing reward only at the exact moment a host reaches zero occupancy.

### No-Controller Baseline (Validated)

Standard scenario (6 hosts, 12 VMs, 60 cloudlets, seed 42), no migrations permitted: **Total energy = 4,090,075 W·sec (≈1.14 kWh)**, makespan matching the historical cloudlet-migration baseline for this scenario (~6149, consistent with the non-power sweep's 6149.35). Cross-checked internally: instantaneous datacenter draw at one mid-run cycle (668.75W) × total simulated seconds (≈6116) ≈ 4.09M W·sec, matching the reported total almost exactly — confirms the accounting is self-consistent, not just plausible-looking.

### Key Finding: Two Distinct, Largely Orthogonal Energy-Saving Levers

Running cloudlet-migration's own `monitor_v1+analyser_v1+planner_v1+executor_v1` (zero power-specific logic, no VM migration at all — only cloudlet-to-cloudlet redistribution within the fixed initial VM/host placement) against the power-instrumented scenario produced **makespan=3100 (49.6% reduction) and total energy=2,006,243.3125 W·sec (50.9% reduction)** — nearly proportional to each other.

This reveals two separable levers, not one:
- **Temporal compression** — finishing the workload faster reduces the *duration* hosts must stay powered at a given level. Since host occupancy was completely unchanged in this run (no VM ever moved between hosts), the ~51% energy reduction came entirely from needing ~50% less total time, not from touching which hosts were on. This lever is *aligned* with makespan minimisation, achieved here "for free" by a controller with no energy awareness at all.
- **Spatial concentration** — reducing the *number* of occupied hosts at any given moment, eliminating static-power floors entirely for hosts driven to zero VMs. This is the classic VM-consolidation lever, and it is the one genuinely in tension with makespan (packing more VMs onto fewer hosts risks contention that lengthens completion time) — the tension flagged in the "would it be feasible to have a cost function" discussion applies specifically to this lever, not to temporal compression.

**Methodological consequence:** the no-controller baseline (4,090,075 W·sec) is the wrong bar for a power-aware Planner to clear. A plain makespan-optimising controller already gets ~51% of that "for free." The real baseline a power-aware Planner must beat is **2,006,243 W·sec** — it only earns its keep by additionally pulling the spatial-concentration lever on top of whatever temporal compression it also achieves.

### Planner Design Implications (Not Yet Implemented)

From working through "what actions would a controller take to minimise energy":
- **Prefer migrating a VM onto an already-occupied destination host over an empty one.** Moving onto a host that's already drawing its static floor costs nothing extra; moving onto an empty host wakes a fresh ~150W floor, which can erase whatever the source-host evacuation just saved.
- **Target complete evacuation of underloaded hosts, not partial de-loading.** With a static-power-dominant curve (60% of draw is fixed), reducing a host's utilization without emptying it captures very little of the available saving — the payoff is concentrated almost entirely at the zero-occupancy boundary.
- **Feasibility guard is mandatory, not optional**: `VmSchedulerTimeShared` has no hard rejection for oversubscription (unlike host-level VM placement), so "would this migration push the destination into OVERLOADED" must be checked explicitly before committing — same discipline already documented for `isSuitableForGuest` (guard, not selection criterion).
- **Statelessness (MAPE, not MAPE-K — an existing, previously-flagged framework limitation) bites harder here than in the other two families.** Fully evacuating a host with several VMs needs multiple consecutive migrations (one action per cycle, per the existing one-migration-per-cycle convention), and the framework has no memory between cycles to track "I'm partway through emptying host X." A stateless greedy Planner will likely still trend toward evacuation over time but may thrash between partially-evacuating multiple hosts rather than completing one.
- **VM scale-in is not currently a supported action.** The original candidate goal was "power via migration/**scaling**," but `ActionSpace` only has `requestVmMigration`/`requestVmCreation` — no VM termination. Migration-only is the current scope; scale-in would be a genuinely new action type, not an extension of an existing one.

### Hand-Coded Power-Minimizing Planner — Design, Implementation, and First Validated Result (2026-07-06)

**Design.** Reused the existing flat `Monitor → double[] → Analyser → LoadState[] → Planner → int[] → Executor` pipeline unchanged — no new interfaces, following the same "press the current data flow to the max" discipline already applied to the cloudlet-migration terminal-GUID rename. The only new element is a redefinition of `LoadState`'s meaning for this Analyser specifically: UNDERLOADED = OFF (host at/near zero CPU demand — genuinely idle, matching `PowerModelLinear`'s own `utilization==0 → 0W` branch), OVERLOADED = FULL (demand at/near the scheduler's hard ceiling of 1.0, per `VmSchedulerTimeShared`'s no-oversubscription guarantee), BALANCED = the only actionable bucket, containing undifferentiated migration sources and destinations.

**Metric choice: CPU demand, not VM count.** VM count was considered and rejected as the classification signal. `PowerModelLinear.getPower()`'s zero-power branch is keyed on aggregate CPU demand being zero, not on VM count being zero — a host holding one VM with no currently-executing cloudlet already reads 0 demand and already draws 0W under the real power model, identically to a literally-empty host. Since the classification should mirror what the reward function itself treats as "off," demand is the more faithful signal, not merely a simpler one. This also resolved an earlier concern about needing two separate metrics (count for OFF, demand for FULL, requiring an unbuilt Fusion stage) — demand alone, with two thresholds (≈0 and ≈1.0), covers both ends within the existing single-`double[]`-per-Monitor contract.

**Anti-oscillation mechanism.** The Planner ranks BALANCED hosts by (re-derived) demand and always migrates from the current minimum to the current maximum. Initially flagged as redundant re-derivation of what the Analyser already computed (the Planner only receives `LoadState[]`, not the underlying `double[]`), but retained deliberately: migrating a VM off the current minimum can only lower it further, and onto the current maximum can only raise it further, so the gap between that specific pair can only widen, never invert, in a single cycle — a constructive guarantee against oscillation, not just a convention. The duplicated demand formula (same arithmetic exists in both the Monitor and the Planner) is accepted as a known, low-risk coupling rather than resolved via an interface change.

**Modules implemented.**
- `Analyser9` — classifies `LoadState[]` from `double[]` demand using `FULL=1.0`/`OFF=0.0` exact-equality thresholds. **Known fragility, not yet fixed**: exact equality on `FULL` is risky given `VmSchedulerTimeShared`'s MIPS-share arithmetic could plausibly return e.g. `0.9999999999997` for a genuinely saturated host, silently misclassifying it as BALANCED. An epsilon-guarded comparison is recommended but not yet applied. GUID naming (`host-demand`/`host-demand-loadstate`) does not follow the established `host-<metric>-<type>` convention (`host-cpu-demand` would be consistent) — left unresolved, to be settled when the generation spec is written.
- `Planner5` — finds the min/max-demand BALANCED hosts (raw entity re-derivation, see above), migrates one VM from min to max, gated by `isSuitableForGuest`. Two bugs found and fixed during review: `mostDemand` sentinel initialized to `Double.MAX_VALUE` (never satisfies `demand > mostDemand`, planner permanently inert) → fixed to `0.0`; `if (demand < leastDemand) {...} else if (demand > mostDemand) {...}` prevented a single host from being evaluated against both running extremes, causing the true maximum to be lost whenever it happened to be the first host processed → fixed to two independent `if` statements. **Known, retained limitation**: `leastLoaded`/`mostLoaded` can resolve to the same host (exactly one BALANCED host, or an exact demand tie — plausible given the small discrete MIPS tier set) with no explicit guard against self-migration; and the Planner tries exactly one destination candidate per cycle with no fallback to a second-best host if the first fails the capacity guard. Both left unfixed deliberately (see below).
- `Executor5` — resolves the `int[]{vmId, hostId}` action (sentinel `{-1,-1}`) to entities and calls `requestVmMigration`, matching the established `executor_v1/v2/v3` pattern. (Root cause of an earlier `ClassCastException`: `Executor2`, from the older `List<VmMigrationPair>`-typed module generation, had been wired to `Planner5`'s `int[]` output — incompatible action types across module generations compile fine under the registry's raw-typed reflection pattern but fail at runtime.)

**Deliberate non-fix: destination fallback.** `Planner5`'s single-shot destination selection (no retry against a second-best candidate) is being left in the hand-coded reference as-is, and the corresponding generation-spec wording will stay silent on this behaviour rather than requiring a fallback — mirroring the cloudlet-migration family's "open-ended feasibility-check wording converged identically across all 5 independently-generated planners" finding. The intent is to see whether independent generations discover a retry/fallback approach unprompted, or replicate this exact limitation, as a genuine test of emergent behaviour rather than compliance with an explicit instruction.

**VM-allocation logging.** Built a one-time, `Log`-independent VM-allocation dump (`System.out.println`, bypassing the static `Log.disable()`/`enable()` state entirely) triggered on the first invocation of the MAPE observation loop inside `HollowedControl`. Necessary because (a) CloudSim's own internal allocation logging was getting buried under subsequent per-tick log volume before terminal scrollback could be reviewed, and (b) the driver's `main()` cannot observe intermediate simulation state at all — `CloudSim.startSimulation()` is a single blocking call, so `main()` only ever sees "nothing placed yet" or "the entire run, including every migration, already finished." The hook has to live inside a `SimEntity` participating in the event loop.

**First test run — First-Fit placement (`VmAllocationPolicySimpler`), same scenario as the QoS family.** Total energy 4,079,375.0 W·sec / avg power 657.96 W, against a no-controller baseline of 4,090,075 W·sec / ~665 W — a ~0.26% reduction, indistinguishable from noise. Diagnosed via the allocation log and per-cycle Analyser output: only two hosts were ever BALANCED (Host0 at 0.9375, Host2 at 0.25, frozen across every logged cycle), and the resulting Host2→Host0 migration attempt was rejected every single cycle by `isSuitableForGuest` — the same "checks provisioned capacity, not runtime utilisation" gap already documented for the QoS family, recurring here. With no fallback destination, the planner produced nothing for the whole run.

**Root-caused why First-Fit is a poor scenario for this objective.** Direct arithmetic on the logged allocation (Host0 = 3750/4000 MIPS committed, Host1 = 4000/4000 exactly, Host2 = 1000/4000, Hosts 3–5 empty) showed the First-Fit placement was already at or very near a local optimum for this specific 12-VM population: Host1 has zero headroom, and Host0's only free headroom (250 MIPS) is smaller than the one VM (1000 MIPS) sitting alone on Host2 — no feasible migration could improve on it. This also explains why avg_power figures near 658–668 W have shown up repeatedly across unrelated-looking experiments (the cloudlet-migration sweep's near-flat ~668 W band, and this run's 657.96 W): all of them are measuring the same static First-Fit placement, since neither cloudlet migration nor this first power-planner attempt ever changes which host a VM lives on. **Methodological note**: First-Fit was deliberately chosen to create imbalance for the load-balancing/QoS objective, but "fill early hosts before touching later ones" is itself a crude consolidation heuristic — the same scenario that stress-tests a balancing controller is close to a best-case, not worst-case, starting condition for a power/consolidation controller. The two families need materially different placement policies to be meaningfully tested; First-Fit only serves one of them.

**`VmAllocationPolicySimple` / `SelectionPolicyLeastFull` — a real CloudSim library bug for initial placement.** Attempted swapping to the stock `VmAllocationPolicySimple` (constructed with `SelectionPolicyLeastFull`) expecting a spread-out, Worst-Fit-style placement. First attempt produced an allocation byte-identical to First-Fit. Root-caused via source inspection: `SelectionPolicyLeastFull` computes host "availability" for `PowerHost` instances as `1.0 - powerHost.getUtilizationOfCpu()`. At the moment CloudSim resolves initial `VM_CREATE` events, no cloudlet has executed anywhere yet, so every host reads exactly 0 utilization — a universal tie. Combined with a strict `>` comparison (never `>=`) and stable list-order iteration, the tie never breaks, so the policy always returns the first not-yet-excluded host — indistinguishable from First-Fit, purely as a tie-break artifact, not a real Worst-Fit decision. This is a genuine limitation of the stock CloudSim 7.x class specific to *initial* placement (its utilization-based signal is only meaningful once workload is already running, e.g. for live-migration destination selection). **Fix**: a custom selection policy (`SelectionPolicyLeastFullByCapacity`) using the scheduler's static/provisioned `getAvailableMips()` — already present as the class's own non-`PowerHost` branch — instead of the `PowerHost`-specific utilization branch. Same sentinel-initialization bug pattern as `Planner5` (`maxAvailable` starting at `0` instead of `-1`) fixed in the same pass.

**Second test run — Least-Full/capacity-based placement, same controller.** No-controller baseline: makespan 6117.01, total energy 6,842,275.0 W·sec, avg power 1118.57 W (sanity-checked by hand: ≈36.5% average utilization across all 6 now-active hosts × [150 + 100×0.365] ≈ 1119 W — matches almost exactly). With the controller: makespan 6200.01, total energy 5,909,384.6875 W·sec, avg power 953.13 W — a **13.6% total-energy reduction, 14.8% average-power reduction**, at the cost of a **1.4% makespan increase**. This is the first real, credited result for this planner (the First-Fit run's 0.26% was noise). The makespan cost is read as the first concrete appearance of the already-documented "spatial concentration risks contention/makespan" tension, not a red flag on its own.

**Migration trace reconstructed exactly** by diffing VM-allocation snapshots at t=100 and t=6100: exactly two migrations occurred over ~61 possible cycles — VM3 (Host3→Host0) and VM1 (Host1→Host0) — correctly driving Host3 to true zero-VM/OFF. The run then stalled: the next min/max pairing (Host1's remaining VM, 1000 MIPS, vs. Host0, now with only 750 MIPS free) fails `isSuitableForGuest` every subsequent cycle, and with no fallback destination, nothing further happens for the rest of the run — even though Host2 (2750 MIPS free at that point) had ample room and a second host could plausibly have been fully drained too. This is empirical confirmation, not just a theoretical worry, that the single-shot destination limitation (see "Deliberate non-fix" above) is the actual binding constraint on how much of the available consolidation gets captured in this scenario.

**Caveat**: single scenario/seed. Per the existing cross-scenario stability findings for the other two families, the 13.6%/14.8% figures should be treated as promising, not validated, until re-run against multiple scenario seeds.

No new System Context needed. User is drafting the Monitor/Analyser/Planner Specification documents (adapting the existing QoS specs) for review against: epsilon-guarded (not exact-equality) thresholds, GUID naming consistency (`host-cpu-demand` convention still unresolved as of this writing), and the Planner spec deliberately staying silent on destination-fallback behaviour (see "Deliberate non-fix" above).

### Forward-Looking: Multi-Objective Fusion (Not Scheduled — Phase 7 Candidate)

Raised as a design question: could a Monitor read multiple signals (cloudlet ETC, host demand, host power) feeding an Analyser-level cost function, producing a controller that optimises a genuine trade-off across makespan/energy/demand rather than a single objective? Assessed as architecturally feasible with a specific recommended shape: a new **Fusion** stage between the Monitor(s) and the existing Analyser, combining several `double[]` Monitor outputs into one composite `double[]` score — leaving `Analyser`/`Planner`/`Executor` contracts completely unchanged, since LoadState classification works identically on a composite score. Two concrete prerequisites, not yet solved: (a) **indexing-domain alignment** — cloudlet ETC is VM-indexed, host demand/power are host-indexed, so Fusion needs an explicit reduction step (e.g. aggregate each host's VMs' ETC) before any elementwise combination is meaningful; (b) the GUID convention's one-to-one string-equality compatibility check would need extending to multi-input matching (Fusion's declared input GUIDs as a set, not a single string) — a second, larger extension of the same kind already done once for cloudlet migration's terminal-GUID reinterpretation. Framing note: with makespan and energy shown to be in genuine tension via the spatial-concentration lever (see above), a composite cost function is properly understood as selecting a point on a Pareto frontier via chosen weights, not converging on one universally "most optimal" state — and characterising which point an LLM-generated composite Analyser implicitly lands on (declared weights vs. actual behaviour) is a natural extension of this project's existing "declared GUID vs. actual internal logic" line of findings (e.g. `planner_v5`). Not started; contingent on all three families being independently validated first. **Update (2026-07-06)**: with the power-family hand-coded planner now validated (13.6% energy reduction, see above) and demand-vs-count and the QoS/power tension both concretely demonstrated, the "all three families independently validated" gate is close to met (hand-coded validation exists for all three; the power family's own 5×5×5×3 generation batch is the remaining piece, now in progress). Sequencing confirmed: pursue Fusion after that batch is independently characterised, not before.

### Multi-Metric Diagnosis Object — Design Sketch (Parked, 2026-07-09)

Explored during the 2026-07-09 GUID-redesign conversation as a candidate shape for multi-metric Monitor output, ahead of any actual Fusion implementation. **Shelved before implementation** — see status note at the end. Captured here so the reasoning isn't lost if Fusion is revisited later.

**Core idea: `Diagnosis`, a fixed 4-field record of `double[]`** — one field per analysis level (`datacenter`, `host`, `vm`, `cloudlet`) — replacing the idea of packing multiple metrics into one flat `double[]` with an implicit layout. Fixing the level dimension at exactly 4 named fields removes the "which order are levels packed in" ambiguity that a single concatenated array would otherwise have.

**Within each level's array**, multiple metrics still fit in a flat `double[]` via two conventions: (a) the spec declares fill order — by-metric (all values for metric 1 across all entities, then metric 2, ...) or by-host/by-entity (all metrics for entity 1, then entity 2, ...); (b) metric count is derived from `length / knownEntityCount` (e.g. `readSpace.getAllHosts().size()` for the host slot) rather than stored explicitly. This yields a free, automatic sanity check — `length % knownCount != 0` is a mechanical, GUID-independent signal that a Monitor/Analyser pairing is broken — at every level boundary.

**Two risks surfaced, not resolved:**
- **Mixed-level packing is genuinely ambiguous, not just complex.** If metrics from two levels were ever packed into one array (e.g. host- and VM-level values concatenated), a consumer dividing by the wrong level's count can still land on a clean integer result — passing the sanity check while being confidently wrong. This is a sharper version of a failure class already seen twice in this project (`monitor_v3`/`v4` sharing a GUID at different aggregation scales; cpu-util vs. cpu-demand diverging under a label that implied equivalence) — "structurally looks fine, is semantically wrong" is this project's most persistent failure mode, and mixed-level packing is a new way into it. Resolution reached: never pack across levels in one array — one array per level, always.
- **The `cloudlet` slot's divisor is not stable.** Unlike `numHosts` (fixed, single-datacenter, no host churn today), cloudlet count changes continuously as cloudlets complete — and will change further once dynamic mid-run cloudlet injection (see 05-scenarios.md, "Stress-Testing Extensions") lands. The divide-check must re-query the *current* count at observation time, never a cached value. This slot is effectively the proving ground for whether the scheme holds up under exactly the complexity increase already planned.

**Two consequences not fully worked through:**
- `Diagnosis` as a 4-field record is a genuine Java-level type crossing the module boundary — a deliberate, bounded exception to the "flat primitive arrays only, no objects across boundaries" principle (01-architecture.md, Key Design Decisions), justified because it's a small fixed documented struct rather than exposed CloudSim entities, but worth flagging explicitly rather than letting it happen implicitly.
- Adopting `Diagnosis` on the Monitor side likely forces a symmetric change to the Analyser's output — a flat `LoadState[]` would throw away exactly the level information the Planner needs (is host 3 overloaded, or VM 7?). Not designed.

**Status: parked, 2026-07-09.** Not required by either current priority (stress-testing extensions or the simplified functional-GUID/self-label design — see 01-architecture.md). Consistent with, not a departure from, this section's existing "not started, contingent on all three families being independently validated first" gating — the multi-metric Fusion prerequisite remains unmet, so building its supporting data structures now would be ahead of need.

**Rationale for shelving, sharpened same day:**
1. **Cost/benefit.** Adds substantial design complexity (4-slot records, per-level divide-checks, cascading Analyser redesign) for a direction that isn't blocking anything currently scheduled — brain power spent here is brain power not spent on the two active priorities.
2. **Doesn't exercise LLM generation, the project's actual research question.** The multi-metric cost function combining fused signals was already decided to be human-authored, not LLM-generated (see 01-architecture.md, "GUID Redesign"). A multi-metric controller therefore doesn't test anything new about *generation* — it mostly grows the human spec-authoring burden. Off the central "can LLM-generated modules compile, integrate, and produce meaningful closed-loop behaviour" question this project exists to answer.
3. **Redundant with the meta-controller's actual job.** See 01-architecture.md, "Fusion via Selection, Not Combination" — this project's answer to "handle multiple objectives" is already meant to be selection across many simple, single-objective controllers (the Controller Library + Meta-Controller), not combination inside one complex controller. Building fusion-within-a-controller machinery competes with, rather than complements, a mechanism already on the roadmap.

Revisit only when Fusion itself is actually scheduled — i.e. after the meta-controller direction has been tried and found insufficient, not before.

### RAM/BW as Additional Metrics — Assessed, Not Yet Implemented (2026-07-06)

Raised as a design question: could RAM or BW be worked into new metrics, and what would optimising them achieve? Two findings, both worth acting on before any implementation:

**Currently degenerate, not just unused.** `createVM` in the current harness hardcodes identical `ram=512`/`bw=1000` for every VM regardless of MIPS tier. Since every VM has an identical footprint, a host's RAM or BW utilization ratio is currently *exactly* proportional to VM count — it would carry zero information beyond what VM count already tells you. This is the same category of trap as the cloudlet-migration family's degenerate `demand` ratio (a signal that looks real but is actually a constant proxy for something else, due to a specific structural property of the scenario). To make RAM/BW genuinely informative, VMs need heterogeneous footprints — a `RAM_TIERS`/`BW_TIERS` array mirroring `MIPS_TIERS`.

**Three distinct candidate goals, not one.** (a) *Multi-resource load balancing* — extending the QoS objective across CPU/RAM/BW together; largely already built (`Analyser5`'s weighted `cpu_util`/`ram_util`/`bw_util` composite already exists) but never the focus of a dedicated generation batch. (b) *Stranded-capacity/fragmentation minimisation* — genuinely new: track the ratio between a host's resource dimensions (is its RAM:CPU balance close to the population average or skewed?) and migrate to correct dimensional skew rather than overall load level — the classic multi-dimensional bin-packing problem, not yet explored here at all. (c) *Feasibility diagnosis* — expose RAM/BW as explicit Monitor signals so `isSuitableForGuest` rejections can be attributed to a specific resource dimension instead of being an opaque black box; a direct extension of the existing "isSuitableForGuest checks provisioned capacity, not runtime utilisation" line of findings.

**No causal connection to the power objective.** `PowerModelLinear` computes power from CPU utilization alone — no RAM term. A RAM-driven controller would not be an alternative lever for the *existing* power objective; it would only move power incidentally via correlation (if RAM-heavy VMs tend to also be CPU-heavy). Genuinely coupling RAM to power would require extending the power model itself (some real hardware power models do include a smaller memory term) — otherwise this is a third, separate objective, not a variant of QoS or power.

Not started; flagged as straightforward to add later given the existing `Analyser5` groundwork, contingent on giving VMs heterogeneous RAM/BW footprints first.

### UtilizationModel Investigation — Resolved: Genuinely Live, But Structurally Unread by CPU Demand (2026-07-07)

Triggered by an unexpected result: swapping `UtilizationModelFull` → `UtilizationModelStochastic` in `createCloudlet` produced zero observable change in demand, makespan, power, or energy. An initial hypothesis that `UtilizationModel` was "vestigial" in this framework was explicitly challenged (correctly) and revised through direct source investigation rather than accepted at face value.

**Two parallel, independent computation pathways confirmed via source** (`CloudletSchedulerTimeShared.java`, `PowerHost.java`, `PowerVm.java`, `HostDynamicWorkload.java`):
- **Allocation-based pathway** — feeds `PowerHost.getPower()`, demand, and makespan. Routes through `CloudletSchedulerTimeShared`'s fair-share MIPS allocation, which never references `UtilizationModel` at all (`getTotalCurrentRequestedMipsForCloudlet`/`getTotalCurrentAllocatedMipsForCloudlet` = `getCurrentCapacity() * cl.getNumberOfPes()`).
- **Cloudlet-utilization-model-based pathway** — `PowerVm.updateCloudletsProcessing()` → `getTotalUtilizationOfCpu()` → per-cloudlet `cl.getUtilizationOfCpu(time)`, feeding `utilizationHistory`. Genuinely reads whichever `UtilizationModel` is plugged in — but this history is only consumed by CloudSim's own built-in VM-consolidation heuristics, which are disabled in this project via `datacenter0.setDisableMigrations(true)`.

**Confirmed empirically, not just architecturally**, via a one-off diagnostic dump of `vm.getUtilizationHistory()`: the Full model produced clean, monotonically-decreasing integer sequences (literal concurrent-cloudlet counts, consistent with the earlier "`UtilizationModelFull` = cloudlet headcount" finding — see CloudSim Observability Constraint below); Stochastic produced continuously-varying, non-integer sequences. The write-side genuinely differs between the two models; nothing in the active module stack (`Monitor7`/`Analyser9`/`Planner5`/`Executor5`) reads it.

**Follow-up: built a new cloudlet-level Monitor metric** to make `UtilizationModel` a live lever rather than leaving it permanently unreadable. Per VM: average (not sum — summing reproduces the same unbounded headcount artefact as the built-in pathway) `cl.getUtilizationOfCpu(now)` over `vm.getCloudletScheduler().getCloudletExecList()`, scaled by `vm.getMips()`; summed and normalised per host by `host.getTotalMips()`. One bug found and fixed: an empty exec list (idle VM) divides by zero, and the resulting `NaN` silently poisons the entire host's sum via `NaN`-propagation through addition — guarded with `execCount > 0 ? ... : 0.0`.

Validating this new metric surfaced a much larger, independent finding — see below.

### CPU Demand Metric Is a Placement Signal, Not an Activity Signal — Root Cause Found (2026-07-07)

While validating the cloudlet-level metric above, a late-simulation window (t=5000–5900, same scenario as the hand-coded power planner) showed the new metric correctly reading exact `0.0` on every host whose VMs had zero cloudlets in their exec list — confirmed against the actual cloudlet finish-time table (all cloudlets on the affected hosts finish by t≈3800 at the latest) — while `vm.getCurrentRequestedTotalMips()`-based demand stayed frozen at a nonzero constant for the entire run, on every host, for thousands of time units after all work provably finished.

The frozen value was shown to be an exact identity, not an approximation: `requestedMips/totalMips` matched `Σ vm.getMips() / host.getTotalMips()` to full precision on every host, every tick. First hypothesis — `Vm.isBeingInstantiated()` stuck `true`, since `Vm.getCurrentRequestedTotalMips()`'s instantiation branch returns exactly `getMips()*getNumberOfPes()` — was tested directly (`vm.isBeingInstantiated()` printed every cycle) and **disproven**: reads `false` from t=100 onward, well before the freeze even sets in. Revised immediately rather than defended.

Root cause found in `CloudletScheduler.java` (abstract base class):
```java
public double getCurrentRequestedTotalMips() {
    double mips = 0.0;
    if (currentMipsShare != null)
        for (double v : currentMipsShare)
            mips += v;
    return mips;
}
```
`currentMipsShare` is set once per tick from the `mipsShare` parameter passed into `updateCloudletsProcessing(currentTime, mipsShare)` — the host-level `VmScheduler`'s allocation decision for that VM, not anything computed from the cloudlet exec list or `UtilizationModel`. Under `VmSchedulerTimeShared`'s no-oversubscription policy, a VM is granted its full requested MIPS ceiling the moment it's placed on a host with room, and that allocation does not shrink when the VM's workload finishes — it is a placement-time fact, not a live-activity signal, despite the misleading method name.

**Consequences:**
- `UNDERLOADED`/OFF (demand == 0) in the power family's `Analyser9` is only reachable when a host has zero VMs assigned — never when a host holds VMs that have simply finished their work. Host-emptying (as achieved by the hand-coded planner's 13.6% result, above) is detected correctly; idle-but-present VMs are invisible to the current metric by construction, not by omission.
- The "frozen demand, no further migration" pattern observed earlier in this project (both cloudlet-migration and power families) is now understood as a structural property of this metric, not scenario-specific equilibrium.
- The existing "monitor_v1/monitor_v2" note below, describing `getCurrentRequestedTotalMips()` as "deterministic and stable: reflects VM workload," is corrected by this finding — it is stable because it reflects VM *placement*, not because it robustly tracks workload.
- **Asymmetric finding, useful for future metric design**: `CloudletScheduler.getCurrentRequestedUtilizationOfRam()`/`getCurrentRequestedUtilizationOfBw()`, immediately adjacent in the same source file, iterate `cloudletExecList` directly and call `cl.getUtilizationOfRam/Bw(time)` — no allocation-share indirection. These correctly read 0 for idle VMs and genuinely reflect whichever `UtilizationModel` is active. The earlier "RAM/BW is currently degenerate" finding (hardcoded identical VM footprints, above) is a separate, orthogonal issue — even setting that aside, the RAM/BW accessor mechanism itself does not share the CPU-demand accessor's placement-vs-activity conflation.

**Not yet decided**: whether to adopt the new cloudlet-level demand metric (or an equivalent RAM/BW-based one) as a genuine replacement/companion signal in a future Monitor variant — doing so would require expanding the approved API to include cloudlet-exec-list access.

### Power Family — LLM Generation Batch, 5×5×5 Run (2026-07-07)

#### Pre-generation decisions (from the UtilizationModel / placement-signal findings above)

- **Stochastic utilization models deferred as future work.** Confirmed that in the current framework `UtilizationModelStochastic` adds no simulation complexity at all: the allocation-based pathway driving demand, makespan, power, and energy never reads the `UtilizationModel`, and nothing in the module stack read the write-side (`utilizationHistory`). Swapping Full→Stochastic is a no-op until activity-based signals are read — which this batch now does, making the model a live lever for a future batch.
- **Approved API extended with the cloudlet exec-list chain**: `vm.getCloudletScheduler().getCloudletExecList()` (non-destructive peek only) + `cl.getUtilizationOfCpu(double time)`, for Monitor and Planner. This exposes activity signals (exec-list membership/count genuinely vary under `UtilizationModelFull` even though per-cloudlet utilization is constant 1.0). Precedent: the cloudlet-migration family already had this chain approved. `host.isSuitableForGuest` removed from the Monitor list (Planner-only, as in the QoS family).
- **RAM/BW accessors deliberately excluded**: under uniform VM footprints + `UtilizationModelFull`, `getCurrentRequestedUtilizationOfRam/Bw` returns the concurrent cloudlet headcount wearing a RAM label — no new signal, guaranteed mislabelling bait. Revisit only after heterogeneous `RAM_TIERS`/`BW_TIERS` exist.
- **Metric vocabulary settled (resolves the naming question left open 2026-07-06)**, restoring the `host-<metric>-<type>` convention: `host-cpu-demand` (placement demand — same GUID as QoS monitor_v2, deliberately, for mixed-pool comparability), `host-cpu-activity` (execution-gated demand — new type token completing the util/demand/activity triple), `host-vm-count` (unchanged from QoS). The spec mandates the empty-exec-list NaN guard explicitly (no experimental value in leaving it open — a NaN'd monitor is garbage, not variation); stays silent on destination fallback and on `isSuitableForGuest`'s role (deliberate, see hand-coded planner's non-fix).

#### Results (Least-Full/capacity-fix scenario, seed 42)

375-row first run; re-run as 5×5×5×1 after confirming the executor slot perfectly non-discriminating (0 of 125 triples with any spread — third family confirmation). All rows completed, no FAILED.

- **Baseline: 1118.57 W avg power**, matching the validated no-controller baseline exactly. Dead-pipeline convergence proxy validated a third time: every INERT pipeline lands on it precisely.
- **Best: 705.35 W = −36.9%** vs baseline — **beats the hand-coded reference (953.13 W, −14.8%) by 2.5×** on captured savings. 11 triples hit it; planner_v3 dominates (best with monitor_v1/v2 across analysers v1–v4; also monitor_v5+analyser_v5+planner_v2/v5).
- Modal outcome 828.37 W (−26%, 43 triples). **No controller performs worse than baseline.**
- **Makespan constant (6117.01) across all 375 rows** including 9-migration runs — no contention cost appears anywhere, unlike the hand-coded run's +1.4%. Consequence: avg_power and total energy are proportional in this dataset; conclusions identical for both.
- Only **10 distinct avg_power values across 125 triples** — many pipelines converge on identical migration sequences; outcome space is coarse.
- **`average_cpu_demand_variance` anti-correlates with avg_power at r = −0.94**: best power controllers produce the *highest* placement variance (0.143 vs 0.007 baseline). The QoS and power objectives are near-perfectly opposed on this scenario — the concrete Pareto-tension number for the Fusion discussion.
- Opportunity cycles uncorrelated with outcome (r ≈ −0.02); best triples execute 6–8 migrations over 61 cycles. "Fewer, well-chosen migrations" replicates for a third family.

#### Three instrumentation defects found and fixed (each validated by exact reproduction of all 125 power values on re-run)

1. **`compatible` = false on all 375 rows.** The reused VM-migration executors still declared `inputGuid: "host-migration-pair"` (pre-rename) vs the planners' `vm-migration` — one stale terminal link zeroed the AND for every row. Fixed. Recommendation adopted going forward: log three per-boundary booleans instead of a single AND so a broken link can't silently kill the axis again.
2. **`actions_proposed` constant at 61 on every row.** The proposal predicate tested against the *cloudlet-migration* family's 3-element sentinel (`new int[]{-1,-1,-1}`); this family's 2-element arrays never match, so the predicate fired every cycle. Fixed to the 2-element sentinel (length-agnostic "any element ≠ −1" form recommended for the mixed pool).
3. **Actionable/opportunity gates redesigned for power semantics.** The inherited OVER∧UNDER opportunity gate read 0 on 48 rows that executed migrations — it encodes QoS source/destination logic, while this family acts on BALANCED hosts. New gates: **actionable = ≥1 BALANCED** ("not at goal state" — all-OFF-or-FULL is simultaneously the consolidation fixed point and a no-action state, since FULL can't receive and OFF can't donate), **opportunity = ≥2 BALANCED** ("a source–destination pair exists"). After the fix, the 15 INERT triples coincide *exactly* with the baseline-convergent set (monitor_v5 × analyser_v1/v2/v4) — the gate correctly identifies dead pipelines for the first time, zero false positives either direction. Side effects: status column not comparable to this family's earlier CSVs; a free derived metric ("first cycle at which actionable goes to 0" = time-to-goal) is available but analyser-relative — compute from ground truth if it's ever used as a claim.

This is the third instance of the "instrumentation carried across families doesn't transfer" pattern (dead variance column in the cloudlet family, quantized makespan under PowerDatacenter, now sentinel shape + gate semantics). Counter predicates, sentinels, and gates must be re-derived per family, not inherited.

**New counter finding once fixed: `actions_proposed == actions_executed` on all 110 active rows** — zero execution failures anywhere. Every generated planner proposes only migrations that pass `isSuitableForGuest` and resolve cleanly (contrast: the hand-coded planner spends most of its run re-proposing one infeasible migration). Planner selectivity, not execution success, is the discriminating quantity in this family.

#### Source-read findings — Monitors

Pool: v1 placement demand (uncapped, `host-cpu-demand`), v2 placement demand (clamped to [0,1], same GUID), v3 activity demand (sum — the spec formula, NaN guard correctly implemented, `host-cpu-activity`), v4 activity demand (**peak**: busiest VM only, same `host-cpu-activity` GUID), v5 VM count (`host-vm-count`).

- **monitor_v1 ≡ monitor_v2, byte-identical across all 125 pairings — "illusory variant diversity", new taxonomy entry.** The only difference is v2's clamp to 1.0, which is dead code: `VmSchedulerTimeShared`'s no-oversubscription invariant already caps the ratio at 1.0 by construction. v1's docstring explicitly claims the uncapped ratio "can exceed 1.0 when a host is overcommitted" — a legal-code, sound-reasoning, **false-in-this-environment premise** (true under `VmSchedulerTimeSharedOverSubscription`, which the spec never ruled out). Distinct from API hallucination and from metric invention: declared design differences along a dimension the environment makes unreachable, detectable only by knowing the scenario's structural invariants. Also means the batch effectively spent two of five slots on one metric.
- **monitor_v4 reuses v3's GUID for a different statistic** (max-per-VM vs sum, different scale: ≤0.25 vs ≤1.0 here). Not dishonest — the convention doesn't specify aggregation — so this is a **GUID vocabulary underspecification finding**, sibling to the LoadState one: `host-<metric>-<type>` distinguishes what is measured but not how it is aggregated; GUID-matched analysers can be calibrated to the wrong scale by a label-identical monitor.
- **Placement monitors (747 W mean) beat activity monitors (~815 W) — metric–reward alignment, not signal quality.** `PowerModelLinear` reads the allocation/placement pathway, so idle-but-present VMs still draw power; activity analysers classify such hosts ≈0 → OFF → excluded as migration sources → the cheapest, still-billing evacuation candidates become invisible. The sweep prices the OFF-definition conflation flagged at spec review at roughly 70 W. Corollary: under an activity-based power model (as real hardware behaves), the ranking would plausibly invert — this is a finding about reward-function structure.
- **monitor_v5 (count) is bimodal, fully explained**: raw counts fed to fixed [0,1]-scale thresholds classify every host FULL/OFF, no BALANCED → INERT (the 15 INERT triples exactly). Adaptive or unreachable-threshold analysers (v3/v5) turn the same signal into best-tier results. Replicates the QoS scale-mismatch/adaptive-analyser finding.

#### Source-read findings — Analysers

All five are the **same single-pass template** — `≤0.0 → UNDERLOADED; ≥ threshold → OVERLOADED; else BALANCED` — differing only in threshold (0.85, 0.80, 8.0, 0.60) plus v5's adaptive mean×1.2-of-active-hosts. Structural convergence (contrast the QoS batch's fixed/stddev/IQR/mean-relative diversity), benign this time. Declared GUIDs: v1/v4 `host-cpu-demand`, v3 `host-vm-count`, v2/v5 activity (see drift below).

- **The epsilon fragility did not materialise**: no module tests `== 1.0`; every FULL test is `≥ 0.60–0.85`. The generated modules are more robust than the hand-coded Analyser9 on exactly the point flagged as its known fragility.
- **analyser_v3's OVERLOADED is nearly unreachable** (`count ≥ 8` with 12 VMs / 6 hosts) → occupied hosts are always BALANCED regardless of input scale — *accidentally* scale-agnostic through threshold unreachability, a different mechanism from v5's genuine adaptivity, but the reason it "rescues" monitor_v5.
- **Cross-batch GUID vocabulary drift — root-caused as spec error, then fixed.** The monitor batch labelled the activity metric `host-cpu-activity`; the analyser batch (v2/v5, whose docstrings unambiguously describe the activity ratio) declared `host-vm-demand`, taken from the spec's older "VM demand" metric name — the vocabulary rename was not carried over to the analyser spec before generation (user-confirmed spec inconsistency, not LLM label instability). Fixed by **manual post-generation edit of analyser_v2/v5's GUID strings** — recorded here for provenance, since published compatibility numbers depend on hand-corrected labels. After the fix: **14/125 triples compatible (11.2%)**. Methodological lesson either way: GUID self-assembly across separately generated module batches stays consistent only if the metric vocabulary is pinned to exact tokens in *every* spec document; the QoS family never hit this because its vocabulary was fully enumerated.

#### Source-read findings — Planners

Declared input GUIDs: v1/v4 `host-cpu-demand-loadstate`, v2/v5 `host-vm-count-loadstate`, v3 `host-cpu-activity-loadstate` (all predicted correctly from compatibility data before reading source). All output `vm-migration`.

- **All five converged, unprompted, on the hand-coded architecture**: BALANCED-only source and destination, min-metric source selection, migrate toward max/tightest/first-fit destination, sentinel otherwise. Spec was silent on strategy; the design space collapsed to one shape parameterised by (source metric × VM-selection rule × destination heuristic).
- **The deliberate destination-fallback non-fix experiment has its answer: all five discovered candidate iteration unprompted.** Every planner scans all destinations with `isSuitableForGuest` as a filter *inside* the loop (first-fit: v1/v5; best-of: v2/v3/v4). None replicated the hand-coded single-shot stall — the opposite outcome from the cloudlet family's convergent feasibility blind spot. This is why proposed == executed everywhere and the main mechanism behind beating the reference 2.5×: the reference stalls when its single candidate is rejected; these keep looking.
- **`isSuitableForGuest` used correctly as a final guard by all five, unprompted** — the QoS family's documented misuse pattern (guard-as-selection-criterion) did not recur despite the spec deliberately staying silent on its role.
- **All five planners' internal logic matches their declared inputGuid** (v1/v4 score by `getCurrentRequestedTotalMips`, v2/v5 by guest-list size, v3 by exec-list utilization) — the spec's "further analysis must match the input analysis" clause held across the whole batch, unlike QoS planner_v5.
- **Why planner_v3 wins — the batch's central finding.** It is the only planner whose internal scoring re-derives *activity* (exec-list utilization via `ReadSpace`): least-active BALANCED source, evacuate that host's highest-contributing VM, most-active suitable destination. Its winning pairings put a *placement* monitor upstream — and the hybrid is why: placement-based classification keeps idle-but-present hosts in the BALANCED pool (activity analysers would misclassify them OFF), then activity-based scoring targets exactly those hosts as least-active sources. **Activity is a bad classification signal but the best planning signal, and the top controller uses each where it works.** Second-family replication of the "best module re-derives its own signal from raw entities" pattern (QoS planner_v5) — but here the declared GUID honestly matches the internal logic: contract-compliant GUID transcendence rather than mislabelling.
- **GUID compatibility still does not predict performance (third family).** Best triple (monitor_v1+analyser_v1+planner_v3, 705.35) is incompatible; compatible mean 776.05 W vs incompatible 822.08 W — compatibility filters some junk, doesn't find winners. planner_v3 appears in zero compatible triples even after the vocabulary fix (no analyser outputs `host-cpu-activity-loadstate` with a matching upstream monitor in the winning pairings).

#### Multi-Scenario Validation — 10 Scenarios, Findings Confirmed (2026-07-07)

125 triples × 10 scenarios (seeds 42–51) in the multi-scenario harness, 1,250 runs. This was the single-seed caveat's required check, and unlike the cloudlet family's equivalent (where the seed-42 best fell to 23rd of 125), **the power family's seed-42 findings survive essentially intact**:

- **Per-scenario baselines via dead-pipeline convergence: validated at scale.** The 15 INERT triples converge to exactly one avg_power value in *every* scenario (nunique = 1, all 10 seeds; baselines 1031.11–1118.57 W, ~8% spread). Per-scenario baselines therefore come free with every sweep; % reductions below are computed per-scenario before aggregating, per the established discipline.
- **planner_v3's dominance confirmed and strengthened.** The top 7 triples by mean per-scenario reduction are all planner_v3, at **43.1% mean reduction (±4.1 s.d., CV 7.8%)** — seed 42 was a slightly below-average scenario for them. Per-slot means: planner_v3 37.1% > planner_v5 36.1% > planner_v2 34.8% > planner_v1 33.0% > planner_v4 29.6%.
- **Ranking stability is much better than the cloudlet family's.** The 11 seed-42 best triples rank [1–7, 18, 22, 27, 28] of 110 active cross-scenario. And the best planner is *not* the most volatile this time: planner_v3 combines top mean with mid-pack CV (8.9%); planner_v4 is most stable (5.6%) but weakest; planner_v5 least stable (10.3%).
- **Placement > activity monitors replicates 10/10 scenarios** (typically 3–8 points of reduction) — the metric–reward alignment finding is not a seed artifact. Count (monitor_v5, 36.4% among active pairings) sits level with placement (36.3%): occupancy-based signals fully suffice when the reward is placement-keyed. monitor_v1 ≡ monitor_v2 to the decimal in all 10 scenarios (illusory-diversity collapse persists, as it must).
- **GUID compatibility fails to predict quality cross-scenario as well**: compatible mean 32.8% vs incompatible 34.3%; best compatible triple ranks 9th. Third family, now at multi-scenario strength.
- **No controller performs worse than baseline in any of the 1,250 runs**; worst active triple still averages −21.3%.

**Headline claim now validated at the same evidentiary standard as the other two families: best generated controller achieves 43.1% ± 4.1 mean energy reduction across 10 scenarios, vs 13.6% (single-scenario) for the hand-coded reference.**

**Timing (power-instrumented runs are ~80× costlier than plain-Datacenter runs).** Steady-state mean 45.25 ms/run (median 44.25, p95 57.5; max ≈330 ms is row-0 JIT warmup, same shape as the cloudlet family's timing run), flat across scenarios and module variants. The cloudlet family ran at 0.61 ms/run — the difference is `PowerDatacenter`'s periodic per-`schedulingInterval` processing (energy interpolation every tick at interval 1, ~6k processing events per run) vs plain `Datacenter`'s sparse event-driven processing; the continuous makespan values confirm the small interval is in use. Consequences: 5×5×5-scale multi-scenario runs are trivially cheap (10 scenarios ≈ 1 min, 100 ≈ 10 min single-threaded), but the eventual 10,000-combo × 100-scenario mixed-pool sweep is ~12.5 h single-threaded for power-instrumented rows. Levers, in preference order: parallelise (runs fully independent — 8 workers → <2 h); raise `schedulingInterval` as a direct cost knob (≈linear speedup, at the price of reintroducing makespan quantization — measure before committing); fall back to 10 scenarios (~75 min) only if necessary.

Running the reference through the same 10-scenario harness is cheap and would make that comparison symmetric. 100-scenario strengthening and the mixed-pool sweep are optional extensions, not validity requirements.

Separately, "makespan constant" is only explicitly demonstrated for the seed-42 single-scenario basis this section extends ("Makespan constant (6117.01) across all 375 rows," 02-family-qos.md-equivalent basis above); the 10-scenario/1,250-run sweep's own write-up never re-certifies makespan constancy for *active* triples across all 10 seeds, only reconfirms INERT-triple baseline convergence (trivial, since INERT takes no action) — an extrapolation carried over, not independently demonstrated. Neither correction changes the qualitative finding; both should be fixed before this comparison is used as a load-bearing number in write-up.

### PowerDatacenter Timing Quantization — Makespan Snaps to 100-Unit Ticks (2026-07-03)

`simulation_results_energy.csv` (375-row cloudlet-migration-module sweep run against the power-instrumented scenario) showed every makespan value as an exact multiple of 100 (range 2100–6200), unlike the original non-power sweep's continuous decimal values (e.g. 3087.44). Confirmed via `df['makespan'] % 100`: 358/375 rows exactly `.00`, remaining 17 off by `0.01` float noise — not coincidental.

**Root cause**: `HollowedControl`'s own MAPE tick cadence (`observationRate=100`) is a separate mechanism from `PowerDatacenter`/`PowerVm`'s internal periodic scheduling tick, which in the current `PowerConstructor.java` is also set to 100. Plain `Datacenter` finalises `CLOUDLET_RETURN` at the exact continuous-time completion event; `PowerDatacenter` only finalises/reports completions at its own periodic tick boundary, snapping true finish times up to the next 100-unit mark.

**Confirmed as a genuine behavioural shift, not a display artefact.** Merged the 343 module-combinations common to both `simulation_results_cloudlet.csv` (orig, plain `Datacenter`) and `simulation_results_energy.csv` (power) on `(monitor,analyser,planner,executor)`:
- `opportunity_cycles` differs in 182/343 (53%), `actions_executed` in 191/343 (56%), `conversion_rate` in 236/343 (69%).
- Only ~50% of rows match a clean `ceil(orig_makespan/100)`, and 18% of combos finish *earlier* under power — rules out "same run, later rounding."
- Moderate correlation (r≈0.55) between makespan shift and opportunity_cycles shift confirms the causal chain: `observeAndAct()` self-reschedules every `observationRate` until `getCloudletList().isEmpty() && submitted==received` fires, so the number of MAPE ticks before termination tracks the (now-shifted) real completion trajectory, which itself shifts because the coarser datacenter tick changes when host/VM state updates land.
- `average_cpu_demand_variance` stays frozen at exactly 0.190647 across all 375 rows — confirms modules' decision logic is unchanged; only the clock granularity they're operating on differs.

**Open fix, not yet applied**: tighten `PowerDatacenter`/`PowerVm`'s internal scheduling interval back to 1 (matching the already-validated `PowerScenarioTest.java`) if/when numeric comparability to the non-power cloudlet-migration sweep is needed. Leave `HollowedControl.observationRate=100` untouched — that's the MAPE cadence, working as designed.

### Average Power vs Total Energy — Total Energy Is a Makespan Proxy, Not a Power-Efficiency Signal (2026-07-03)

Prompted by the question of whether a continuous (non-batch) workload framing should target average power rather than total energy. Computed `avg_power = total_energy / makespan` across all 375 rows of `simulation_results_energy.csv` (cloudlet-migration modules only, no VM migration):

- `total_energy` correlates with `makespan` at r≈1.0 — under this instrumentation, total energy is almost entirely a restatement of how long the run took, not a genuine power-efficiency measurement of the controller.
- `avg_power` across all 375 combinations is nearly flat: 668.40–668.64 W, a **0.036% relative spread** — every cloudlet-migration controller, including the fully inert (0 migrations) case, draws essentially the same average power.
- The residual signal is real but small: `avg_power` correlates -0.49 with `actions_executed` and -0.77 with `conversion_rate` (more migration activity → modestly lower average power), correctly signed but swamped by a near-constant floor.

**Likely mechanism**: the calibrated model is `PowerModelLinear(250, 0.6)` → `power = 150 + 100×utilization` per host. Even a fully idle host still draws its 150W static floor under this formula. Unless `PowerDatacenter`'s total-power summation explicitly excludes zero-VM hosts (rather than calling `getPower()` on all hosts regardless of occupancy), evacuating a host removes only its ≤100W dynamic slice, never its 150W static contribution — which would contradict the "empty host = 0W" ground-truth semantic already decided (Phase 1) but not yet confirmed as actually enforced at the summation level. **RESOLVED 2026-07-08 — empty host contributes 0W at the summation level, confirmed empirically.** In the random-scenario seed-42 anchor run (see "Mixed-Pool Preparation" below), a draw with one fully empty host reported total energy matching the hand computation `Σ_occupied(150 + 100×u) × makespan` almost exactly (968.75 W × 6256.01 ≈ 6.06M W·sec vs reported 6,059,531.25); an idle-but-on 150W floor for the empty host would have added ~940k W·sec. The "empty host = 0W" semantic is enforced end-to-end.

**Empirical confirmation via a second data point**: running the VM-migration family's load-balancing controller (objective: minimise cross-host CPU-demand variance) on the same power-instrumented scenario gave **Total energy = 6,779,386.1875 W·sec, avg_power = 1093.45 W** — a **~64% increase** (1093/668 ≈ 1.64×) over the cloudlet-migration ceiling. Mechanistically consistent: minimising demand variance requires spreading VMs across *more* hosts to equalise load, which is structurally the opposite of consolidation — every additional host carrying any VM pays its full static floor continuously. Cloudlet-migration never moves VMs at all, so it inherits whatever the initial First-Fit placement produced (incidentally more consolidated) rather than actively working against consolidation. Rough back-of-envelope against the calibration (`150+100u` per active host, 6 hosts max): 668W is consistent with only ~3–4 hosts carrying load continuously; 1093W is consistent with something close to all 6 hosts being kept warm.

**Reconciles both findings**: intra-host cloudlet scheduling barely touches `avg_power` (0.036% spread) because it never changes *which* hosts are powered; inter-host VM placement is where the real leverage is — but only if the objective favours consolidation. The existing VM-migration Planner does the opposite by design (load-balancing ≠ energy-minimising), giving a concrete empirical worst-case (1093W) alongside the near-inert cloudlet-only floor (668W) as bounds for the energy-aware Planner (Phase 3) to land between.

### VM MIPS Scaling — Built, Root-Caused, Fixed, and a Deeper Bypass Found (2026-07-10)

Built `monitor_ETC`/`monitor_v4` (per-VM ETC, sum-based after an initial single-cloudlet-max false start), `analyser_ETC`/`analyser_v2` (median/MAD classification into OVERLOADED/BALANCED/UNDERLOADED), `Planner6` (scales the first OVERLOADED VM up one `MIPS_TIERS` step, skipping VMs already at the top tier), `Executor6`, and a new `ActionSpace.requestMipsScaling(GuestEntity vm, double newMips)`.

**First implementation was a complete no-op.** `vm.setMips(newMips)` alone produced bit-identical makespan/energy logs across runs despite the log visibly showing MIPS values changing. Root-caused via full CloudSim source trace (`Vm.java`, `CloudletScheduler.java`, uploaded and read directly): `Vm.getCurrentRequestedMips()` only reads `getMips()` while `isBeingInstantiated()` is true (effectively t≈0 only); afterward it delegates to `CloudletScheduler.getCurrentRequestedMips()`, which just echoes back `currentMipsShare` — a value seeded once at initial host allocation via `VmScheduler.allocatePesForGuest()` and never independently re-derived from `vm.getMips()` again. `setMips()` changes a number nothing downstream ever reads.

**Fix**: `requestMipsScaling` calls `vm.getCloudletScheduler().updateCloudletsProcessing(getNow(), newMipsShare)` directly, forcibly reseeding `currentMipsShare`. Verified working on the original `{250,500,1000}`-tier/60-cloudlet scenario: makespan 6200.01→5800.01, energy 6,824,375→6,376,875 W·sec.

**Follow-up experiment (extended `MIPS_TIERS` to `{250,500,1000,3000}`, cloudlets 60→36) produced the opposite of the predicted result**, and tracing it surfaced a more important finding than the original hypothesis. Predicted: raising the ceiling and shrinking the workload should *amplify* the already-flagged idle-but-scaled power cost (a VM scaled up then left idle still draws power under the placement-based model). Observed instead: Controller average power **1025.18 W** vs Baseline (no controller) **1056.02 W** — the controller *beats* baseline more clearly than before, and total energy is lower too (3,485,625 vs 4,799,600 W·sec), not just average power.

**Root cause of the flip, from the full per-cycle log:**

1. **The fix bypasses the exact mechanism that should cap it.** `updateCloudletsProcessing()` writes straight into the VM's own `CloudletScheduler`, never through `Host`/`VmScheduler.allocatePesForGuest()` — the only code path that checks a request against the host's real per-PE cap (`VmSchedulerTimeShared`: `if (mips > peMips) return false;`, `peMips` = 1000 here) and decrements the host's actual `availableMips`. **Confirmed empirically**: VMs *born* demanding 3000 MIPS on their single PE (`pesNumber=1`) are silently rejected at creation — VM5 and VM10 (both drew the 3000 tier from the RNG at t=0) never appear in the VM Allocation log and process zero cloudlets for the entire run. Yet `Planner6`/`Executor6` scaling an *already-running* VM (VM1, VM3, VM6) to that identical 3000 MIPS mid-run succeeds without complaint and visibly changes its processing rate. The same value is structurally impossible through normal allocation and trivial through the scaling fix's direct write. Any result from the current `requestMipsScaling` at tiers above `peMips` is exploiting this scheduler/executor consistency gap, not demonstrating a physically valid capacity increase.
2. **This scenario's setup makes makespan reduction an almost free energy win, which swamped the predicted idle-inflation cost.** `datacenter0.setDisableMigrations(true)` and a fixed host-VM binding mean all 6 hosts stay powered (and pay their static floor, `PowerModelLinear(250,0.6)` → 150+100×utilisation per host) for the *entire* makespan regardless of load. The superphysical MIPS boost let VM1/VM3 (laggards holding up the finish line) blow through their backlog, shrinking makespan by ~25% (4545.01 baseline → 3400.01 controller). Static floor alone (150W×6×1145 time-units ≈ 1.03M W·sec) accounts for most of the ~1.31M W·sec total-energy gap — directly extending the "total energy is a makespan proxy" finding above to this family's own controller, not just cross-family.
3. **The predicted idle-but-scaled waste does occur, just outweighed.** VM6 is toggled to 3000 MIPS at t=2100 — the same tick its last cloudlet (cloudlet 5) finishes. The scale-up bought it nothing; VM6 then sits idle at an inflated, per-PE-impossible 3000 rating from t=2100 to the run's end (t=3400), a 1300-unit wasted tail exactly matching the original hypothesis. It just costs far less than the makespan collapse saves in this particular parameterisation.

**Consequence**: `requestMipsScaling` needs rebuilding to route through `Host`/`VmScheduler.allocatePesForGuest()` (capped at `peMips`, can genuinely fail against host capacity) rather than writing `CloudletScheduler` state directly, splitting it into two distinct action types — "maximise MIPS within the VM's current PE allocation" (bounded by construction) and "increase the VM's PE allocation" (the only legitimate way past a single PE's ceiling, and per `CloudletScheduler.updateCurrentCapacity()`'s `capacity /= Math.max(pesInUse, cpus)`, only pays off when the VM has multiple cloudlets genuinely concurrent — a no-op for serial one-at-a-time VMs regardless of PE count). See 01-architecture.md, "VM MIPS Scaling — Implementation, Root Cause Fix, and a Deeper Design Problem," for the architectural framing, and 07-limitations.md for the itemised trap-list entries. **Not yet rebuilt** — current implementation stands as a documented, unresolved bypass.

**Separate, general finding surfaced by the same trace: `analyser_v2`'s median/MAD classification has no absolute anchor, and combined with a one-directional (scale-up-only) Planner, structurally ratchets toward maximum allocation over a run's tail.** Classification is relative to the *current* live population, not a fixed reference — as VMs finish they report `etc=0`, dragging the median toward 0, so a VM whose own absolute ETC hasn't changed can flip from BALANCED to OVERLOADED purely because its peers finished (directly observed: VM8 sits at a near-constant absolute ETC across t=1800–2100 while its classification would tip as the median collapses around it). With no scale-down action to correct for it, any VM still running late in a simulation eventually gets classified worst-relative-to-peers and escalated, regardless of real need. This is a **spec-completeness gap**, not a GUID-detectable failure: an Analyser built exactly to its interface contract (`Analyser<M,D>`) can still produce this drift, because nothing in "classify relative to current state" forces consideration of the population-thinning tail case. A human author would plausibly add an absolute floor unprompted (fixed ETC ceiling independent of live population, comparison against the *initial* t=0 median rather than a continuously-refreshed one, or a utilisation/efficiency framing — actual throughput vs. assigned capacity — instead of relative standing). Logged as a design-space finding for Analyser specs generally, not specific to this one module.

### VM MIPS Scaling — Bypass Closed, Confound Isolated and Confirmed (2026-07-14)

Closes out the bypass documented above. Per the split-action design (01-architecture.md, "VM MIPS Scaling — Split Into Separate Actions, Cascade Rejected"), `requestMipsScaling` now clamps every request to the VM's real per-PE ceiling via a new `ReadSpace.getHostCapacity(vm)` accessor (`vm.getHost().getGuestScheduler().getPeCapacity()` — single source of truth, also used by the analyser). `analyser_ETC2`'s not-yet-maxed filter was updated to check `vm.getMips() < readSpace.getHostCapacity(vm)` instead of the nominal `MIPS_TIERS` top — closing a second bug this surfaced: gating on the nominal tier list instead of the real per-host ceiling left VMs stuck at their true ceiling permanently "not yet maxed," producing an infinite retry loop (same VM re-selected and re-clamped every cycle, log showing a repeated "toggling to 3000" that was never actually applied) until the real-capacity check replaced it.

**Clean before/after confirms the theoretical prediction from the original bypass writeup.** Re-ran the `{250,500,1000,3000}`-tier/36-cloudlet scenario both with and without the fix. Pre-fix (bypass active): the "3000 available" run finished faster and cheaper (t=3100, 3,168,750 W·sec) than the "3000 unavailable" baseline (t=3400, 3,691,875 W·sec) — the exploit's signature. Post-fix (clamp + real-ceiling analyser, both bugs closed): the "3000 available" run is now the **worse** of the two (t=4200, 4,330,625 W·sec) — a full reversal, and worse than the honest baseline, not just no-longer-better.

**The reversal is not itself further evidence of a bug — it's the VM-creation-rejection confound, isolated for the first time.** VM#5 and VM#10 (born at 3000 MIPS in the "available" scenario) are rejected at creation on this host (real cap 1000, `pesNumber=1`) and never appear in the VM Allocation log — confirmed present in every version of this run, pre- and post-fix. All 36 cloudlets concentrate onto the 10 VMs that did deploy (avg 3.6/VM) instead of a clean 12-way split (avg 3.0/VM). Under `CloudletSchedulerTimeShared`'s `capacity /= max(pesInUse, cpus)`, more cloudlets sharing the same fixed per-VM capacity is a genuine throughput headwind, not a neutral side effect. Pre-fix, the bypass's illegitimate 3x rate boost more than compensated for that headwind, making the run look faster. Post-fix, nothing compensates for it, so the concentration penalty shows through cleanly — confirming the two effects were stacked the whole time, and the "3000 tier" was never actually helping on its own merits.

**Separate, still-open gap, not fixed here**: `requestMipsScaling`'s clamp checks the single-PE ceiling (`peMips`) but still writes directly to `CloudletScheduler.updateCloudletsProcessing()`, never through `Host`/`VmScheduler.allocatePesForGuest()`. It therefore never checks or decrements the host's aggregate `availableMips` budget — a VM could in principle still be granted a rate the *host in aggregate* can't really back, even though it can no longer exceed what a single PE could deliver. Distinct from, and narrower than, the bypass just closed. See 07-limitations.md.

### VM PE-Count Scaling — Built, Two Real CloudSim-Mechanism Bugs Found and Fixed (2026-07-14)

Second half of the split-action design (01-architecture.md). Built `analyser_ETC3` (argmax-ETC among VMs that are simultaneously MIPS-maxed via `getHostCapacity`, contended — `pesInUse > vm.getNumberOfPes()`, summed from `getCloudletScheduler().getCloudletExecList()` — and sitting on a host with room), `Planner7`, `Executor7`, and `ActionSpace.requestPeScaling(GuestEntity vm)`. Own P-E GUID suffix (`3004`); action payload is `int[1]` (VM id only) rather than the `int[2]` used by migration/MIPS-scaling — no second element is meaningful for this action (there's no PE-index parameter to carry, see below), and cloudlet-migration's own `int[3]` action already established that payload length should track genuine information content rather than a fixed convention. A same-shaped-but-different-meaning array was judged a worse risk than a differently-shaped one: a length mismatch fails loudly (`ArrayIndexOutOfBoundsException`) the same way the GUID level digit already forces crash-over-silent-corruption at the M-A/A-P bridges; a padded, unused sentinel slot would not.

**First mechanism bug: `Pe.status` (FREE/BUSY) is dead code under `VmSchedulerTimeShared`.** Confirmed via direct source read (`Pe.java`, `VmSchedulerTimeShared.java`): neither `setStatusFree()` nor `setStatusBusy()` is ever called anywhere in the time-shared scheduler's allocation path — both are documented in `Pe.java`'s own javadoc as "should be used by SPACE shared hostList only." Every `Pe` sits at its constructor-default `FREE` forever under time-sharing, regardless of real occupancy. The original `Planner7` design (iterate `host.getPeList()`, pick the first `Pe` with `getStatus() == Pe.FREE`) was therefore checking a field that never changes — always "finds" PE #0 free, independent of actual host load. The real per-host capacity signal under time-sharing is `VmScheduler.availableMips`, a single aggregate MIPS budget, not a per-PE flag; `ReadSpace.hostHasFreePe(vm)` was rewritten from a `Pe.status` scan to `host.getGuestScheduler().getAvailableMips() >= host.getGuestScheduler().getPeCapacity()`. Consequence for `Planner7`: there is no "which specific PE" decision to make at all under this scheduler — `allocatePesForGuest` takes a MIPS-share list, never a PE id, and bin-packs it across physical PEs internally via `updatePeProvisioning()`. The whole PE-selection loop was removed, not just its comparison fixed — this is also why the action payload dropped to `int[1]`.

**Second mechanism bug: `VmSchedulerTimeShared.allocatePesForGuest` uses replace, not additive, semantics, and does not credit back a VM's existing allocation before checking a resubmitted total.** Confirmed via source and reproduced empirically: submitting `currentShare + one new entry` as the VM's new mips-share list makes the method's internal admission check (`getAvailableMips() < totalRequestedMips`) test the VM's *entire* reconstructed allocation against whatever's currently available — not just the incremental new PE — because the VM's already-held portion was subtracted from `availableMips` at the time it was originally granted and is never returned before the new, larger total is checked. Result: every claim beyond a VM's second PE failed deterministically (`success=false`, confirmed via targeted debug logging showing `requestedShareSize=3` failing against an `availableMips` that hadn't been credited for the VM's first two PEs), while `analyser_ETC3` kept re-selecting the same VM every cycle since neither `hostHasFreePe` nor the eligibility filter had any way to know the last attempt silently failed. Fix: `host.getGuestScheduler().deallocatePesForGuest(vm)` before the replacement `allocatePesForGuest(vm, newShare)` call, returning the VM's current allocation to the pool first so the new total is checked against a correctly-credited baseline. Verified via debug logging (`success`, `availableMipsAfter`, `numberOfPes` printed per call): post-fix, claims succeed cleanly through however many PEs a VM's real contention and host capacity support, `availableMips` arithmetic checks out exactly against the real VM Allocation log (host total capacity independently confirmed at 4000 MIPS/host — 4×`peMips` — by solving the pre/post-claim `availableMips` deltas against a known co-tenant's non-1000 allocation), and the run converges to "no bottleneck" instead of looping.

**Design decision alongside this build: `ActionSpace` methods stay `void`, not converted to `boolean`, despite this action's own `allocatePesForGuest` naturally returning one.** Considered and rejected making `requestPeScaling` (or the whole interface) return success/failure: `Executor.execute()`'s own boolean return is what currently drives the `actionsExecuted` counter, and — confirmed by inspecting `Executor7` — it only distinguishes "a real action was attempted" (non-sentinel) from "sentinel, nothing to do," never "the underlying ActionSpace call actually succeeded against real capacity." That's already true uniformly across every existing action type, not something newly introduced here. Selectively giving one action's `ActionSpace` method a real outcome-level boolean while every other method (and the existing `actionsExecuted` metric) stays attempt-level would mean "success" means different things for different action types in exactly the kind of cross-family-comparable metric this project has already been burned by (see "Instrumentation carried across families fails silently," 07-limitations.md). If outcome-level tracking is ever needed, it should be a uniform addition — post-hoc state inspection across every action type — not a one-off signature change. See 07-limitations.md.

### VM PE-Count Deallocation — Built, Naming Finalised, Two ReadSpace Promotions (2026-07-15)

Symmetric counterpart to PE-count allocation above. `requestPeScaling` renamed to **`requestPeAllocation`**, paired with a new **`requestPeDeallocation(GuestEntity vm)`** — deliberate rename over reusing `requestPeScaling` for both directions: allocate/deallocate are triggered by opposite analyser conditions (OVERLOADED-needs-more-PEs vs. UNDERLOADED-has-idle-PE) and are exactly the "same shape, semantically distinct" case the GUID suffix convention already exists to disambiguate, not a single parameterised action — adding a direction flag to one method would reintroduce the same hidden-branching pattern already rejected for the MIPS-scaling cascade (01-architecture.md). Each stays a fixed, always-one-PE operation (no target-count/delta parameter) — matches the one-allocation-per-cycle discipline by construction rather than by convention.

`requestPeDeallocation` mirrors the allocation method's deallocate-then-reallocate fix (same replace-semantics bug applies symmetrically) plus a floor guard (`currentShare.size() > 1`, mechanical minimum-of-1-PE, kept in `ActionSpace` — a *demand*-based floor, i.e. don't shrink below what active cloudlets need, is deliberately left to the analyser's eligibility gate instead, same read/act separation already established for allocation). One review-caught bug before it shipped: `List<Double>.remove(peMips)` returns a boolean indicating whether a match was actually found, silently discarded in the first draft — if `getAllocatedMipsForGuest(vm)`'s entries ever weren't exactly `peMips`-valued (plausible given `requestMipsScaling` still doesn't route through `allocatePesForGuest`, see below), `newShare` would stay unshrunk while `numberOfPes` still decremented, desyncing the VM's PE count from its real allocation. Fixed by checking the return and aborting (with a log line) on no-match, matching the "crash/abort over silent corruption" discipline already applied to the GUID scheme and the PE-allocation replace-semantics fix.

**`getPeDemand(GuestEntity vm)` promoted from inline analyser logic to a `ReadSpace` primitive.** Previously computed ad hoc inside `analyser_ETC3` (sum of `cl.getNumberOfPes()` over `vm.getCloudletScheduler().getCloudletExecList()`); now a named `ReadSpace` method both the allocation- and deallocation-trigger analysers call, rather than each independently re-deriving it. Deliberate methodological reasoning, not just tidiness: this is a closed-form calculation — one correct value, no legitimate alternative strategy — so leaving it as LLM-generated code inside each analyser wouldn't test anything about strategic diversity (this project's actual research question), only risk correctness drift that would masquerade as diversity under a MOSS-style similarity measure (a broken reimplementation "looks different" from another broken reimplementation exactly as much as two genuinely different valid strategies do — the metric can't tell them apart without a correctness oracle). Same reasoning already applied to `getHostCapacity`/`hostHasFreePe`: facts about the world belong in `ReadSpace`, decisions belong in the generated modules. See 07-limitations.md.

**`hostHasFreePe` re-parameterised from `GuestEntity vm` to `HostEntity host`** — straight signature replacement, not an overload (the one existing call site, `analyser_ETC3`, was trivially rewired to `hostHasFreePe(vm.getHost())`, so keeping a redundant VM-form purely to avoid a one-line edit wasn't worth the extra surface). Motivation: the VM-parameterised form can only ever answer "does *my own* VM's current host have room" — useless for evaluating a migration-destination *candidate* host that no VM belongs to yet. `getHostCapacity` was deliberately **not** given the same treatment — no current caller needs to evaluate a bare candidate host's ceiling, only ever the host a specific VM already sits on, so generalising it now would be speculative.

### PE-Scaling Controller — Confound-Free Result and the Sticky-Allocation Energy Cost (2026-07-15)

Two harness bugs found comparing `PowerScenarioTestControl.java` (PE-allocation controller) against `PowerScenarioTest.java` (no-controller baseline), both invalidating every prior comparison between them: **datacenter scheduling interval** (`PowerDatacenter` constructor's last argument) was `100` in the control file vs. `1` in the baseline — an independent knob from the broker's own MAPE `observationRate` (also 100), controlling how often the datacenter itself finalises cloudlet completions. This reproduces exactly the PowerDatacenter timing-quantization mechanism already documented above (2026-07-03) — every non-scaled VM's cloudlets in the control run were rounding up to the next 100-unit tick, inflating apparent makespan for VMs the controller never touched. **Utilization model** was `UtilizationModelStochastic` in the control file vs. `UtilizationModelFull` in the baseline — a different simulated workload, not a controller-behaviour difference. Both fixed (scheduling interval → `1`, utilization model → `UtilizationModelFull`).

**Clean re-run confirms both were real confounds and isolates the actual effect.** Post-fix, every untouched VM's cloudlet finish times are bit-for-bit identical between control and baseline runs, and overall makespan matches exactly (3746.01 both) — definitive evidence PE-allocation has zero collateral effect on VMs/hosts it doesn't act on, superseding an earlier (already-retracted, see prior session) "physical PE contention" hypothesis. The four PE-scaled VMs (#0, #9, #10, #11) still finish substantially earlier than baseline — the local speedup is real — but none of them sit on the critical path (VM#4, never PE-scaled, gates overall makespan both with and without the controller), so the local wins buy nothing at the system level. Total energy is **+12.2%** over baseline (4,699,194 vs. 4,189,719 W·sec) for **zero makespan benefit**, now attributable entirely to real mechanism rather than measurement noise.

**Root cause: PE allocation is one-directional with no deallocation trigger wired in.** Every PE claimed to relieve a transient bottleneck stays allocated — and counted against host utilisation — for the remaining ~3700 time units of the run, long after the VM that needed it has cleared its backlog. `requestPeDeallocation` (above) now exists as a mechanism but nothing calls it yet; no analyser triggers a release. This confound was masked in every earlier PE-scaling number by the scheduling-interval/utilization-model bugs and is now cleanly isolated for the first time.

### First Multi-Controller Test — Rate-Scaling → PE-Scaling Switch Beats Both Single-Controller Baselines (2026-07-15)

First real test of the `Selector`/`Controller`/`ControlUnit` refactor (01-architecture.md, "Selector / Controller / ControlUnit"). Two controllers registered — `controller-mips-scaler` (`analyser_ETC2`/`Planner6`/`Executor_v1`) and `controller-pe-scaler` (`analyser_ETC3`/`Planner7`/`Executor7`) — with a hardcoded, one-shot time-based switch (`selected = controllers.get(1)` at `t≥1500`) as a mechanism smoke test, not a real switch rule (see 01-architecture.md for why goal-directed selection stays out of scope for now).

**Result beats every prior baseline simultaneously**: 3,090,431 W·sec energy / 2672.01 makespan, vs. no-controller baseline (4,189,719 W·sec / 3746.01) and PE-scaling-alone (4,699,194 W·sec / 3746.01, see above) — **≈26% less energy and ≈29% less makespan than doing nothing**, and both single controllers' own results beaten at once. Not pursued — real switch logic is explicitly out of scope for this refactor (01-architecture.md); this run's purpose was proving the switching *mechanism* works and that composition beats either controller solo, both now demonstrated.

### VM PE-Count Deallocation Trigger — Built, Infinite-Retry Bug Fixed, Sticky-Allocation Cost Closes 59% (2026-07-15)

Built `analyser_ETC4`/`Planner8`/`Executor8`, the deallocation-trigger sibling to `analyser_ETC3`/`Planner7`/`Executor7`, closing the root-cause gap identified above ("PE allocation is one-directional with no deallocation trigger wired in"). Selection rule, arrived at through several revisions: primary rank is `argmax(numberOfPes(vm) - getPeDemand(vm))` — PE slack — not ETC; slack targets the actual sticky-allocation problem directly (which VM is holding the most PEs beyond what it currently needs), where ETC only measures remaining work and doesn't indicate over-provisioning. Ties on slack are broken by **largest** ETC, not smallest — reclaiming from the VM that would otherwise hold its idle PE longest captures the most energy savings; a "smallest ETC, minimize thrash risk" alternative was considered and rejected, since ETC doesn't reliably predict whether a VM's demand will spike back up.

**Infinite-retry bug found on first test run, same class as `analyser_ETC2`'s original one (07-14).** Eligibility was gated on `diff > 0` alone (`numberOfPes - peDemand`), which doesn't account for `ActionSpace`'s mechanical minimum-1-PE floor (`currentShare.size() > 1`, from the build above). A VM sitting at exactly 1 PE with 0 demand still nominally has "1 PE of slack" under that formula, so it kept getting selected and rejected — `"Unable to deallocate a PE from VM#0"` — every single cycle for the remainder of the run (17+ wasted cycles in the first full test, `t=2100` through `t=3700`), with zero state effect but silent pollution of any attempt-count metric (`Executor8` returns `true` unconditionally on any non-sentinel attempt, matching the established attempt-level `actionsExecuted` convention). Fixed by adding `numberOfPes(vm) > 1` to the eligibility gate, mirroring the `ActionSpace` floor directly instead of re-deriving it independently.

**Baseline methodology**: rather than a separate single-controller-for-the-whole-run comparison, the no-deallocation baseline keeps the same `t≥1500` `Selector` switch structurally identical to the real test, varying only the destination (deallocator vs. no active `ControlUnit` after the switch) — a tighter control, isolating exactly one variable rather than also varying the switch mechanism itself.

**Result: deallocation recovers ≈59% of the sticky-allocation energy cost, zero makespan cost.** Same scenario/seed as the First Multi-Controller Test above, confirmed by an exact match on the allocation-alone figure. Three-way comparison: no controller = 4,189,719 W·sec; allocation-alone = 4,699,194 W·sec (**+12.2%**, reproduces the confound-free result above exactly); allocation+deallocation = 4,399,719 W·sec (**+5.0%**). Deallocation closes 299,475 of the original 509,475 W·sec gap (≈59%) with makespan bit-identical across all three conditions (3746.01). Residual ~5% overhead attributed to allocation-to-release lag, not a further bug: PEs are only released once a VM's demand has already dropped to zero (not proactively), bounded by the 100-unit `observationRate` between the bottleneck clearing and the next MAPE cycle catching it.

### Rate-Scaling and Load-Balancer Bug Fixes — SelectorScenario (2026-07-16)

All three bugs below were found against `SelectorScenario.java`, testing the existing controllers (`controller-mips-scaler`, `controller-pe-scaler`, `controller-pe-descaler`, and `controller-load-balancer`) under the newly-built dynamic cloudlet injection (05-scenarios.md, "Dynamic Cloudlet Injection"). None of the underlying controller logic changed in intent — every fix below closes a gap between what the log claimed happened and what the simulation state actually reflected.

**Bug 1 — `requestMipsScaling` silently overwritten within ~1 time unit, explaining a "4x MIPS boost, near-zero makespan effect" puzzle.** A rate-scaling run showed VM1 and VM7 both correctly identified as bottlenecks and correctly scaled 250→500→1000 MIPS over the run (confirmed via `availableMipsAfter`/log lines), yet overall makespan barely moved (8382.17→8381.17, ~0.01%) and total energy went the wrong way (+1.02% vs. baseline). Traced to `requestMipsScaling` writing `((Vm) vm).setMips(boundedMips)` and pushing a manually-built mipsShare straight into `CloudletScheduler.updateCloudletsProcessing()`, bypassing `VmScheduler` entirely — the same bypass already flagged in 07-limitations.md for exceeding a single VM's per-PE cap, but with a second, more damaging consequence: `VmSchedulerTimeShared`'s own `mipsMapAllocated` record is never updated to match. `PowerDatacenter`'s regular `Host.updateCloudletsProcessing()` cycle (`schedulingInterval=1` in this scenario) pulls straight from that stale record every ~1 simulated time unit and pushes it back into the VM's scheduler, silently reverting the boost almost as soon as it's applied. Confirmed via full source trace across `Host.java`, `CloudletScheduler.java`, `VmSchedulerTimeShared.java` — not guessed.

Fix, verified against `VmScheduler.java`/`GuestEntity.java` source before shipping (both `allocatePesForGuest`/`deallocatePesForGuest` are declared on the abstract `VmScheduler` base class, and `getHost()` is declared directly on `GuestEntity`, so no unsafe casting is needed):

```java
public void requestMipsScaling(GuestEntity vm, double newMips) {
    if (!(vm instanceof Vm)) return;
    double peMips = getHostCapacity(vm);
    double boundedMips = Math.min(newMips, peMips);
    List<Double> newMipsShare = new ArrayList<>();
    for (int i = 0; i < vm.getNumberOfPes(); i++) newMipsShare.add(boundedMips);

    Host host = vm.getHost();
    VmScheduler scheduler = host.getGuestScheduler();
    scheduler.deallocatePesForGuest(vm);           // credit back the VM's own current share first —
    boolean success = scheduler.allocatePesForGuest(vm, newMipsShare); // allocatePesForGuest doesn't do this itself

    if (!success) {
        List<Double> originalShare = new ArrayList<>();
        for (int i = 0; i < vm.getNumberOfPes(); i++) originalShare.add(vm.getMips());
        scheduler.allocatePesForGuest(vm, originalShare); // restore rather than leave deallocated
        return;
    }
    ((Vm) vm).setMips(boundedMips);
    vm.getCloudletScheduler().updateCloudletsProcessing(getNow(), newMipsShare);
}
```

The `deallocatePesForGuest` call first is required, not optional — `VmSchedulerTimeShared.allocatePesForGuest` uses replace-not-additive semantics and doesn't credit back an existing allocation before checking a new total (same mechanism already documented for PE-count scaling, 07-limitations.md), so calling `allocatePesForGuest` directly on an already-allocated VM would leak MIPS/PE-count on the host with every scale rather than fix anything.

**Bug 2 — fixing Bug 1 surfaced a real infinite-retry bug in `analyser_ETC2`.** Once `requestMipsScaling` correctly persisted its boosts, VM1 got stuck: "Toggling VM#1 to 500 MIPS" fired at every single cycle across multiple rotation windows (t=100–1900, 3000–4400, 4500–4900) and never advanced or resolved to "No bottleneck found." Root cause, traced through the actual numbers: Host0's 8 resident VMs summed to exactly 4000/4000 MIPS — the host is genuinely, permanently full. `analyser_ETC2`'s eligibility check (`vm.getMips() < greatestMips && vm.getMips() < readSpace.getHostCapacity(vm)`) only tests the candidate VM's own value against two absolute, VM-local ceilings; it never checks whether the VM's *host* actually has spare aggregate capacity for the next tier. That check is only correct in a world where a VM's headroom is bounded solely by its own ceiling — true only if hosts aren't meaningfully shared, which `VmSchedulerTimeShared` doesn't guarantee (see 07-limitations.md, oversubscription entry). Every cycle, `requestMipsScaling`'s new deallocate-then-reallocate path correctly failed (confirmed: freeing VM1's own 250 MIPS only ever created 250 of headroom against a 500 MIPS request) and rolled back, so `vm.getMips()` never actually changed — and `analyser_ETC2` re-selected the same unchanged, still-eligible-looking VM next cycle. Same bug class as `analyser_ETC2`'s original infinite-retry bug (07-14) and `analyser_ETC4`'s PE-deallocation bug, this time downstream of the newly-fixed rate-scaler rather than a missing mechanical floor.

Confirmed harmless-but-wasteful, not silently corrupting: `deallocatePesForGuest` fully rebuilds a host's entire PE-allocation map on every call (not just the target VM's), so every failed retry causes real churn across all 8 co-resident VMs' bookkeeping (specific physical-PE assignment can shuffle, though not their allocated MIPS totals, since `updatePeProvisioning()`'s reallocation loop iterates a `HashMap` with no guaranteed order) — real cost, even though the numbers produced were sane.

Fix — `hostHasRoomForNextTier`, added as an additional eligibility condition in `analyser_ETC2.analyse()`:

```java
private boolean hostHasRoomForNextTier(GuestEntity vm, int[] tiers) {
    int position = -1;
    for (int i = 0; i < tiers.length; i++) {
        if (vm.getMips() == tiers[i]) { position = i; break; }
    }
    if (position < 0 || position + 1 >= tiers.length) return true; // unknown/top tier — existing checks handle it

    double nextTier = tiers[position + 1];
    int pes = vm.getNumberOfPes(); // this controller rotates with PE-scaling on the same VM pool —
                                    // a candidate can genuinely hold more than one PE
    double currentTotalShare = vm.getMips() * pes;
    double nextTierTotalShare = nextTier * pes;

    Host host = vm.getHost();
    double spareForThisVm = host.getGuestScheduler().getAvailableMips() + currentTotalShare;
    return nextTierTotalShare <= spareForThisVm;
}
```

Verified via re-run: VM9, VM8, VM10 (on Host1, which had genuine spare capacity) correctly scale in three clean successive cycles, then "No bottleneck found" from t=400 onward for the rest of an ~8000-unit run — no repeats, no retries. Host0's VMs (including the confirmed critical-path VM7) correctly never get selected again, because there genuinely is no room — this is now a correct, trustworthy negative result, not a bug.

**Bug 3 — `Planner4` (load-balancer) searched the global VM list instead of scoping to the overloaded host.** Independently found while testing the load-balancer (`controller-load-balancer` / `Analyser8`/`Planner4`/`Executor5`) against a worst-case placement scenario: `Executor5` perpetually migrated the same VM back and forth between the two most-underloaded hosts every single cycle, while the genuinely overloaded host was never touched — 52 migrations across a full run with zero effect on any cloudlet's completion time. Root cause: `Planner4`'s "find VM using most MIPS" loop iterated `readSpace.getVmList()` (every VM in the datacenter) rather than the specific `host` currently being evaluated as overloaded. Several VMs tied at the datacenter's highest MIPS tier, the comparison was strict `>`, and the first VM in list order won the tie every time regardless of which host it actually lived on — so the same global-max-MIPS VM got proposed no matter which host tripped the threshold, and the target-host selection (first `UNDERLOADED` host in list order) chased whichever of two near-empty hosts that VM had just vacated, producing an endless ping-pong.

Fix: change the inner "find VM using most MIPS" loop's source from `readSpace.getVmList()` to `host.getGuestList()`. Verified via re-run: correctly selects a genuine resident of the actually-overloaded host, converges to a stable balanced state within 1-2 cycles instead of thrashing for the remainder of the run.

### Combined Load-Balancer + Rate-Scaling Result — First Genuine Makespan Win (SelectorScenario) (2026-07-16)

With all three bugs above fixed, `controller-load-balancer` was run for the first time alongside `controller-mips-scaler`/`controller-pe-scaler`/`controller-pe-descaler` in the same rotation, against the stochastic-injection scenario (05-scenarios.md). Every prior test of these controllers against this scenario — load-balancer alone, rate/PE-scaling trio alone — had shown zero effect on makespan; this is the first combination to move it.

**Mechanism, traceable line by line in the log.** VM7 (250 MIPS) was independently confirmed, across the whole preceding investigation, to be the scenario's critical-path bottleneck, permanently stuck because its host (Host0) was committed at exactly 4000/4000 MIPS from t=0 — no amount of correctly-behaved rate-scaling could ever free room for it (Bug 2 above). At t=1500 the now-fixed load-balancer activates, finds Host0 overloaded, and migrates VM4 off it — the first time in the whole scenario Host0 has ever had anything removed. At t=2000, `analyser_ETC2` immediately finds the new headroom and scales VM1, VM3, **VM7**, and VM2 — VM7's first-ever successful scale-up, made possible only because Host0 finally had spare capacity. At t=3500 the load-balancer migrates VM5 off Host0 too, opening further room, and at t=4000–4100 VM1 and VM7 are scaled again, to 1000 MIPS.

**Result: makespan 8382.17 → 5809.17 (−30.7%).** Cloudlet 79 (on VM7, the confirmed critical-path cloudlet) dropped from Time=4284.66 (finish 8382.17) to Time=389 (finish 4486.51) — a ~91% cut in its actual processing time, directly attributable to VM7's MIPS increase finally taking hold. This is the first time in this entire stochastic-scenario investigation that any controller or combination has moved the terminal (makespan) metric rather than only its own internal diagnostic.

**Not a free win — real, substantial power cost.** Total energy: 4,702,583.04 W·sec (**+21.3%** vs. no-controller baseline). Average power: 809.51 W (**+75%**). Every previously-empty host (Host2–5) is now active, hosting VM4/VM5/VM8/VM1, and running at collectively higher MIPS — a genuine, sustained power cost for the speed gain, the mirror image of this project's existing consolidation-for-energy finding (fewer active hosts → lower power, worse makespan; here, more active hosts + real capacity relief → much better makespan, real power cost). Read as a clean demonstration of a genuine performance-vs-power tradeoff, not evidence either objective is "wrong" — see 01-architecture.md, "Goals vs. Mechanisms," and 02-family-qos.md for how this connects to the broader question of what host-migration is actually for.

**Caveat on generality, not yet resolved:** `Planner4` selects by current MIPS demand, not by any notion of "who's on the critical path" — VM7 specifically benefiting here is not guaranteed by the mechanism, it happened because VM4/VM5 (the VMs `Planner4` did select) shared a host with VM7 and freeing them happened to free VM7's headroom too. A scenario where the critical-path VM shares a host with nothing else worth migrating would not obviously see the same result. Not yet tested.

### Cost — Identified as a Missing Objective, Not Yet Built (2026-07-16)

`DatacenterCharacteristics`'s `cost`/`costPerMem`/`costPerStorage`/`costPerBw` fields (set once in `createDatacenter`, present in every scenario file including `SelectorScenario`) are never read back out anywhere in this project's history — confirmed by grepping every "cost" mention across the whole `handoff/` tree; all refer to energy cost or design-complexity cost, none to billing. Processing cost is cheap to add retroactively without new instrumentation: standard CloudSim billing computes it as `cost` (per-second rate) × `Cloudlet.getActualCPUTime()`, and `getActualCPUTime()` is exactly the "Time" column already printed in every `OUTPUT` table this project has produced. Memory/storage/bandwidth cost are not currently actionable — nothing in the action space touches VM RAM, disk, or a cloudlet's declared data footprint, so those components would need new design-space work before being meaningful to report.

**Cost and energy are demonstrably not the same axis, evidenced by two runs already in hand, not yet quantified.** The worst-case-placement (First-Fit, no controller) run won on energy specifically by tolerating more contention (3.48M vs. 4.19M W·sec, packing onto 3 hosts instead of 6) — since contention inflates `getActualCPUTime()`, that same run would very plausibly *lose* on cost. Conversely, the load-balancer-only run (pre-bug-fix baseline, before it was combined with rate-scaling) cost +32% energy for a byte-identical `OUTPUT` table — zero change to any cloudlet's completion time means zero cost impact either, so that run is a pure cost+energy loss with no offsetting benefit on any axis. Neither has been computed as an actual cost number yet — flagged as the next concrete, low-effort addition. Not yet built; candidate for its own `08-family-cost.md` if it grows past a single retrofitted column on existing runs.

### Cost — Two-Part Model Built, First Reconciled Result (2026-07-17)

**Built as two separate components rather than one merged number, deliberately.** Component 1, usage-cost, is exactly the retrofit proposed above: `cost × Σ getActualCPUTime()`, summed over `broker.getCloudletReceivedList()` after `runSimulation()` returns. No new instrumentation needed for this to cover injected cloudlets too — `HollowedControl`/`Selector` extends `DatacenterBroker`, and CloudSim's own `processCloudletReturn()` appends every completed cloudlet to that list regardless of which `submitCloudletList()` call (initial batch or later injection) it arrived through, so the existing list is already the correct aggregate. Component 2, uptime/energy-cost, converts the datacenter's already-tracked total energy into dollars via a new `CostCalculator.wattSecondsToDollars()` utility (`PRICE_PER_KWH` rate constant, `getPower()`'s W·sec total ÷ 3.6M × rate).

**A dedicated host-active-seconds tracker (subclassing `PowerDatacenter`) was considered and rejected.** The design was fully scoped — override `updateCloudetProcessingWithoutSchedulingFutureEventsForce()`, snapshot host occupancy before calling `super()` (since the superclass strips completed VMs off hosts before returning), accumulate per-host active-seconds in the same per-interval loop that already computes `timeFrameHostEnergy` — but not built. Reason: this project's own power model is static-power-dominant (~60% of draw fixed per active host, and that floor already drops to zero for hosts driven to zero VMs, per the "two separable levers" finding above), so total energy is already a near-linear proxy for host uptime. A dedicated tracker would have mostly re-derived the existing energy figure in different units, for real added instrumentation and bug surface, with no genuinely new information — not worth it unless a future need specifically requires uptime decoupled from power draw (e.g. modelling flat per-instance-hour billing).

**Rate constants reconciled to real-world scale for the first time.** The original `cost = 3.0`/CPU-second (inherited from `ConstructorVariableVM.java`, itself lifted from CloudSim's own `CloudSimExample3` toy demo) turned out to be roughly 5-6 orders of magnitude larger than real cloud CPU-second pricing (~$0.00001/vCPU-sec, e.g. AWS ≈$0.17/hr ÷ 4 vCPU ÷ 3600 ≈ $0.0000118/vCPU-sec) once compared directly against a genuine market rate (`PRICE_PER_KWH = 0.12`, an average retail electricity price). Taken literally, the old constant implied a run costing hundreds of thousands of dollars in compute against pennies in electricity — not a plausible ratio for any real datacenter. Rescaled `cost` down to ~1e-5/CPU-second so usage-cost and energy-cost are both genuine, comparable dollar figures rather than one arbitrary and one real; this was a pure linear rescaling (confirmed by both cost totals below preserving the exact ratio of the original "cost unit" totals: 669,906→391,833 units and $2.2330→$1.3061 differ by the same constant factor).

**First reconciled result, same scenario/seed as the 2026-07-16 combined-controller makespan win** (Load-Balancer + MIPS rate-scaling + PE-allocation, vs. no-controller baseline):

| | Compute cost | Energy cost | **Total** |
|---|---|---|---|
| Baseline | $2.2330 | $0.1292 | **$2.3622** |
| Controller | $1.3061 | $0.1568 | **$1.4629** |

Energy cost's +21.4% matches the 2026-07-16 entry's +21.3% total-energy figure almost exactly (both derived from the same underlying energy total, just rescaled). Net total cost still favours the controller by a wide margin — the compute-cost win from relieving VM7's contention dominates the energy-cost penalty from waking additional hosts — but the margin (−38.1%) is meaningfully smaller than compute-cost alone would suggest (−41.5%), because the two components are pulling in opposite directions.

Not needed for the single-seed comparison above, since the injected cloudlet stream is identical between baseline and controller runs (controllers reallocate resources, they don't add or remove cloudlets).

**Not yet done, flagged as the immediate next step before trusting −38.1% as a real finding:** this is a single run on a single scenario/seed. Every other headline number in this project (43.1%±4.1 energy across 10 scenarios, QoS's 20-seed stability check) was validated across multiple scenarios before being treated as a finding; this cost result hasn't had that treatment yet. ### Cost — Extended to Four Components: BW/Egress and Storage Added (2026-07-17)

**Built as the practical payoff of the cloudlet file/output size realism work** (05-scenarios.md, "VM RAM/BW Footprint — Realism Pass" section covers the parallel VM-side work; cloudlet length/file/output size distributions are the cloudlet-side counterpart, same session). Randomising file/output size alone was confirmed to have zero effect on any tracked metric — neither `computeCost` nor `energyCost` ever read it, and CloudSim's own file-size mechanics (network transfer delay) aren't engaged in this single-datacenter setup — so it was pure inert scaffolding until billing was added.

**Two new cost components, deliberately given different formulas rather than both rescaled from the existing `costPerBw`/`costPerStorage` constants.** `DatacenterCharacteristics` documents all four of its cost fields identically as "$ per second," but real-world bandwidth/egress billing is per-GB-*moved*, not per-second-of-capacity-*held* — a genuine billing-model mismatch, not just a scale problem like the original `cost=3.0` constant. Resolved by treating the two components differently:
- **BW/egress cost**: `PRICE_PER_GB_TRANSFER = 0.09` ($/GB, real-world egress rate, consistent across AWS ≈$0.09, Azure ≈$0.087, GCP ≈$0.12), billed once per cloudlet against `(fileSize + outputSize)`, summed over `newList` the same way `cpuTimeTotal` already is. This is the interpretation that actually makes the file/output size randomisation matter — it was chosen specifically because it's the only one of the two that does.
- **Storage cost**: `PRICE_PER_GB_SECOND_STORAGE = 3.09e-8` ($/GB-sec, derived from real block storage pricing ≈$0.08/GB-month, AWS EBS gp3), billed against total VM disk footprint (`Σ vm.getSize()` across `vmlist`) × makespan — this one *does* fit CloudSim's native $/sec convention, since storage genuinely is a continuously-held-over-time resource in reality, unlike bandwidth.
- `costPerMem` deliberately left unbuilt: no clean standalone real-world analog (RAM is bundled into instance price in virtually every mainstream offering, not metered separately), and would likely be redundant with compute cost anyway given RAM's exact-linear-multiple relationship to MIPS (collinearity finding above) — same "don't build inert/redundant scaffolding" reasoning applied earlier to the rejected memory-optimized VM tier idea.

### Resource Utilization Ground Truth — Peak/Average RAM & BW Tracking, Built, Bug Found and Fixed (2026-07-17)

**Design decided against continuous CloudSim-event hooking.** RAM/BW are statically allocated per VM at placement time (unlike CPU, which fluctuates continuously with scheduling), so utilization only changes at discrete migration events. Two designs were weighed: hooking into `requestVmMigration` (the `ActionSpace` method) to update the metric exactly when a migration is attempted, versus simply polling host state once per MAPE cycle inside `updateGroundTruth()`. The polling approach — proposed directly by the project owner — was confirmed to be better, not just easier: hooking into `requestVmMigration` would only capture attempted migrations, not confirmed outcomes (the method fires a zero-delay `send()`, not a synchronous state change), reintroducing the same attempt-vs-outcome ambiguity already documented for `actions_executed` elsewhere in this project (07-limitations.md). Once-per-cycle polling sidesteps that ambiguity entirely and matches the existing energy-sampling precedent (`PowerDatacenter` also computes its ground truth on a fixed cadence, not event-by-event).

**Implemented as a new helper, `updateResourceUtilizationGroundTruth(hosts)`, called from the `updateGroundTruth()` orchestrator** alongside the pre-existing `updateDemandVarianceGroundTruth(hosts)` — per the project owner's explicit architectural intent that `updateGroundTruth()` become the single place the `Selector` evaluates all ground-truth signals, decomposed into named sub-methods rather than one growing monolith.

**First implementation was a real, if quiet, design bug: aggregating across the whole datacenter makes the metric structurally blind to migration.** The first version summed RAM/BW demand and capacity across *all* hosts combined, then divided once (`totalRamUsed / totalRamCapacity`). Validated by the first controller run showing peak exactly equal to average (40.63%, both RAM and BW) — identical to the no-controller baseline — despite the controller in that run (`controller-load-balancer`, which migrates VMs) clearly having had a real effect on energy and makespan. Root cause: migration reassigns which host's tally a VM's RAM/BW counts under, but changes neither the VM's own demand nor any host's capacity — so the datacenter-wide numerator and denominator are both mathematically invariant to migration by construction. The aggregate can only move if VMs are created/destroyed or hosts added/removed, none of which happen here. Tracking "peak vs. average" only has a point if peak can register a transient, migration-driven concentration on one host even while the whole-datacenter total stays fixed — an aggregate formulation can never do that, no matter how many migrations occur.

**Fixed by computing per-host utilization each cycle and rolling the *max across hosts* into peak, not the datacenter-wide sum:**

```java
private void updateResourceUtilizationGroundTruth(List<HostEntity> hosts){
    double maxRamUtilThisCycle = 0, maxBwUtilThisCycle = 0;
    double sumRamUtilThisCycle = 0, sumBwUtilThisCycle = 0;

    for (HostEntity host : hosts) {
        double hostRamUsed = 0, hostBwUsed = 0;
        for (GuestEntity vm : host.getGuestList()) {
            hostRamUsed += vm.getRam();
            hostBwUsed += vm.getBw();
        }
        double hostRamUtil = hostRamUsed / host.getRam();
        double hostBwUtil = hostBwUsed / host.getBw();

        maxRamUtilThisCycle = Math.max(maxRamUtilThisCycle, hostRamUtil);
        maxBwUtilThisCycle = Math.max(maxBwUtilThisCycle, hostBwUtil);
        sumRamUtilThisCycle += hostRamUtil;
        sumBwUtilThisCycle += hostBwUtil;
    }

    // Peak = the single worst host, at its worst moment across the whole run
    peakRamUtilization = Math.max(peakRamUtilization, maxRamUtilThisCycle);
    peakBwUtilization = Math.max(peakBwUtilization, maxBwUtilThisCycle);

    // Average = mean across hosts this cycle, averaged again across cycles
    ramUtilizationSum += sumRamUtilThisCycle / hosts.size();
    bwUtilizationSum += sumBwUtilThisCycle / hosts.size();
    utilizationCycleCount++;
}
```

**Validated by the fix doing exactly what it was meant to.** Re-run of the same combined-controller scenario (Load-Balancer + rate-scaling + PE-allocation) now shows **peak RAM/BW util = 75.00%, average RAM/BW util = 40.63%** — peak genuinely diverges from average for the first time, correctly registering that migration concentrated VMs onto one host at some point in the run even though the datacenter-wide total (still 40.63%, matching baseline) never moved. The no-controller baseline correctly still shows peak = average = 40.63% for both signals — consistent with zero migrations, as expected with no controller present.

**RAM and BW peak at the identical 75.00% value — the collinearity finding (07-limitations.md) reappearing a third time.** Since every VM's RAM/BW are exact linear multiples of its MIPS and host RAM:MIPS/BW:MIPS ratios are the same fixed constants, any host reaching a given RAM utilization reaches the identical BW utilization simultaneously — now confirmed true not just for aggregate/mean utilization but for the per-host peak signal too. Getters (`getPeakRamUtilization()`, `getPeakBwUtilization()`, `getAvgRamUtilization()`, `getAvgBwUtilization()`) added alongside the existing `getGroundTruthAvgVariance()`, same div-by-zero guard pattern.

### VM/Cloudlet Core Count — Pre-Implementation Review of the PE-Scaling Controller Stack (2026-07-20)

Ahead of actually wiring `CORE_TIERS` into `createVM`/`createCloudlet` (00-INDEX.md, current priority), reviewed every module in the PE-allocation/deallocation controller chain — `monitor_ETC`, `analyser_ETC3`, `analyser_ETC4`, `Planner7`, `Planner8`, plus the underlying `Selector.requestPeAllocation`/`requestPeDeallocation` (already reviewed 2026-07-16) — for hardcoded `pesNumber=1` assumptions that heterogeneous VM core counts would break.

**Clean: `Planner7`/`Planner8` and the gating logic inside `analyser_ETC3`/`analyser_ETC4`.** Neither planner references PE count at all — both just scan `LoadState[]` for the first OVERLOADED/UNDERLOADED VM and return its id, generic regardless of the VM's actual core count. `analyser_ETC3`'s `peDemand > vm.getNumberOfPes()` gate and `analyser_ETC4`'s `diff = vm.getNumberOfPes() - peDemand` with its `vm.getNumberOfPes() > 1` floor guard are both relative comparisons already written correctly for VMs with more than one PE — consistent with `getPeDemand()` having been deliberately promoted to `ReadSpace` for exactly this purpose (07-limitations.md, 2026-07-15).

**Bug found and fixed: `monitor_ETC`'s ETC formula was per-PE-blind.** `demand = totalRemainingLength / vm.getMips()` used the VM's per-PE rate as if it were the VM's total throughput, ignoring `CloudletSchedulerTimeShared`'s actual capacity-sharing behaviour (`capacity /= Math.max(pesInUse, cpus)`, already documented 2026-07-14). Invisible under `pesNumber=1` everywhere (per-PE rate and total throughput are identical with one PE); would have silently overstated ETC — making busy multi-core VMs look more bottlenecked than they really are — the moment `CORE_TIERS` went live, since dynamic injection plus `RANDOM_ASSIGNMENT` already routinely stack multiple concurrently-executing cloudlets on one VM. Verified against `CloudletSchedulerTimeShared.java` source (`getTotalCurrentAvailableMipsForCloudlet = getCurrentCapacity() * cl.getNumberOfPes()`), cross-checked with the already-verified `capacity` formula rather than assumed. Fixed and confirmed implemented:

```java
int peDemand = readSpace.getPeDemand(vm);
double effectiveThroughput = vm.getMips() * Math.min(peDemand, vm.getNumberOfPes());
double demand = (effectiveThroughput > 0.0) ? (totalRemainingLength / effectiveThroughput) : 0.0;
```

**Still open, blocking cloudlet-side PE variation specifically — VM-side `CORE_TIERS` wiring is unblocked and can proceed independently.** What CloudSim actually does when a cloudlet requests more PEs than its assigned VM has is unverified. `RANDOM_ASSIGNMENT` is uniform and blind to VM properties (07-limitations.md, 2026-07-20), so once cloudlets can request >1 PE this mismatch becomes a routine occurrence, not an edge case — needs a source check or empirical test before enabling cloudlet-side core-count variation.

### VM Core Count — First Validated Runs (2026-07-20)

**Design decided: `CORE_TIERS[randomInt]` deterministically coupled to the same tier index as `MIPS_TIERS`/`RAM_TIERS`/`BW_TIERS`** (Small=1, Medium=2, Large=4), not a separate probabilistic roll gated by tier. Mirrors real cloud instance-family convention (core count is part of the fixed SKU, not independently random within one) and keeps VM sizing internally consistent with how RAM/BW were already coupled. The "not every big VM is fully parallelized" concern that motivated considering a roll belongs on the cloudlet side instead — cloudlet PE demand, independently drawn and decoupled from cloudlet length, is the correct place for that variation (still blocked pending the CloudSim capacity-mismatch question, 07-limitations.md).

**First run (seed 49) validated allocation but not deallocation.** VM#11 (Small tier, correctly started at `cpus=1`) hit genuine demand (`peDemand=2 > cpus=1`) and `requestPeAllocation` correctly grew it to 2 PEs — first real confirmation of the fixed `monitor_ETC`/`analyser_ETC3` chain operating on a true multi-core-capable population. But the run's makespan (792.72) finished before the scheduled t=1000 switch to `controller-pe-descaler`, so deallocation was never exercised — compounded by seed 49 already being flagged as an atypically fast, assignment-lucky scenario (see "Seed 49 Investigated" below).

**Second run (seed 42, full-length) found a real bug: the `getHostCapacity(vm)`-vs-`vm.getMips()` mismatch in `requestPeAllocation`/`requestPeDeallocation`** — see 07-limitations.md for the full mechanism. **Third run (same seed, post-fix) confirmed the fix, with a real downstream effect beyond the immediate log line.** VM#0 and three further Medium-tier VMs (VM#6, VM#8, VM#9) that hit the same deallocation path later in the run all succeeded cleanly. More importantly: `Analyser8` (the load-balancer, a completely separate controller) had read Host#1 and Host#3 as permanently "overloaded" for the entire buggy run because VM#0's stuck PE kept inflating Host#3's placement demand; post-fix, Host#3 reads "balanced" from the very first load-balancer cycle after the deallocation succeeds, and by the second load-balancer window all four hosts read balanced. The bug was corrupting cross-controller host-state perception, not just failing silently in isolation. Energy dropped 3,659,722.92 → 3,585,080.65 W·sec (−2.04%) between the buggy and fixed runs, consistent with several previously-stuck PEs actually being released; makespan unchanged (these are idle VMs shedding unneeded cores, not anything on the critical path).

**Status: VM-side `CORE_TIERS` wiring is validated and this bug class is closed.** Cloudlet-side PE-count variation remains the one blocked item (00-INDEX.md).

### Cloudlet PE Count — Built and Validated (2026-07-20)

**Design: independent weighted draw, decoupled from cloudlet length, gated by the same `CORE_TIERS` values as the VM side.** `UniformDistr(1, 101, CLOUDLET_PE_COUNT_SEED)` sampled once per cloudlet, bucketed 1–80 → `CORE_TIERS[0]` (1 PE), 81–95 → `CORE_TIERS[1]` (2 PEs), 96–100 → `CORE_TIERS[2]` (4 PEs) — mostly-serial, occasionally-parallel, matching real cluster-workload literature on job parallelism. Deliberately not coupled to cloudlet length or to the assigned VM's own core count, unlike the VM-side tiers — job parallelism doesn't track job size the way instance core count tracks instance size (see the earlier design discussion: VM core count is a capacity/purchasing decision, real families make it deterministic; cloudlet PE demand is a workload property, real traces show it's only weakly correlated with size). Reuses the existing `UniformDistr`-then-cutoff mechanism already established for `batchSizeDist`, rather than introducing a new distribution class.

**Bug found and fixed before it could bite: `UniformDistr` constructed locally inside `createCloudlet()` would have reset every batch to the identical roll sequence.** `createCloudlet()` is called 11 times per run (1 initial batch + 10 injections) — the same "RNG recreated per call" bug class already root-caused once this session (`lengthRng`/`assignRng` as local variables, 05-scenarios.md) very nearly recurred in a new form. Confirmed via direct read of `UniformDistr.java`: its `(min, max, seed)` constructor builds its own internal `UniformRealDistribution` and calls `reseedRandomGenerator(seed)` immediately — it owns its RNG state entirely, unlike `LognormalDistr`, which wraps an externally-supplied, already-persistent `Random` object. So `LognormalDistr`'s "construct fresh each call" pattern is safe (state lives in `lengthRng` outside the call), but the identical-looking pattern applied to `UniformDistr` is not (state lives inside the object itself). Fixed by hoisting `coreCountDist` to a `private static final UniformDistr` field, constructed once at class level and never rebuilt — matching how `batchSizeDist` avoids the same bug simply by being declared once in `main()`, never inside a repeatedly-called function.

**Cloudlet-vs-VM PE-count mismatch confirmed safe by direct source read, closing the item that had blocked this work.** `CloudletScheduler.updateCurrentCapacity()` (the abstract base class, not the `TimeShared` subclass — verified directly, not inferred): `capacity = Σ currentMipsShare; capacity /= Math.max(pesInUse, cpus)`, where `pesInUse` sums `cl.getNumberOfPes()` across every cloudlet in the exec list and `cpus = currentMipsShare.size()`. No admission check anywhere — `cloudletSubmit()` adds a cloudlet to the exec list unconditionally. A cloudlet requesting more PEs than its VM has is never rejected; it's proportionally throttled down to exactly the VM's real total capacity (worked example: 2-core VM, one cloudlet requesting 4 PEs → `capacity = vm.getMips()×2/4`, that cloudlet's allocated MIPS = `capacity×4 = vm.getMips()×2`, i.e. the VM's full capacity, no more). Also confirmed algebraically exact, not approximate: the already-fixed `monitor_ETC` formula (`vm.getMips() × Math.min(peDemand, vm.getNumberOfPes())`) reduces to precisely the real total-throughput value in both the `pesInUse ≤ cpus` and `pesInUse > cpus` regimes when worked through this verified formula. No compatibility gate needed between `RANDOM_ASSIGNMENT` and cloudlet PE demand — CloudSim's own scheduler handles the mismatch gracefully.

**First validation run (seed 42, full combined-controller scenario) shows a real, traceable throughput effect, not just successful wiring.** PE-deallocation continued succeeding cleanly on every VM that hit it (no regression from the earlier bug fix), and the load-balancer resolved Host#1 from overloaded to balanced exactly as in the pre-cloudlet-PE-variation run. Makespan increased from 4000.43 to 4802.51 (+20%) versus an otherwise-identical run without cloudlet PE variation — the first sign the mechanism has genuine scheduling consequences, not just cosmetic wiring.

**Confirmed via direct cloudlet-level tracing, not just aggregate makespan.** Cloudlet #13 landed on VM#1 in both runs — proof `assignRng`'s sequence is genuinely unaffected by `coreCountDist` (separate RNG streams, as designed) — but its actual CPU time grew from 116 to 330 (≈2.84×). Start time was identical (0.01) in both runs, ruling out a scheduling-timing shift; the slowdown is a pure throughput/contention effect, consistent with either cloudlet #13 itself rolling a higher PE count and getting diluted on VM#1's single core, or another elevated-PE-demand cloudlet sharing VM#1's exec list concurrently with it. Either way, confirms the mechanism is doing exactly what it was built to do.

**Status: cloudlet-side PE-count variation is validated and closed. VM/cloudlet core count is now fully done on the realism checklist.**

### Host Failure — CloudSim Mechanics Pre-Implementation Check (2026-07-20)

Before scoping a host-failure stress-testing extension (05-scenarios.md's original 2026-07-09 stress-testing pair, alongside dynamic cloudlet injection which is already built), checked what CloudSim's pinned 7.x build actually supports natively, per this project's "verify before trusting" discipline. **Finding: `Host.isFailed()`/`setFailed()` exists and is genuinely settable, but appears to be read nowhere in the active processing path** — see 07-limitations.md for the full source-grounded writeup (same class of finding as the already-documented `Pe.status` dead-code result). **Finding: `Datacenter.processVmMigrate()` carries CloudSim's own unresolved `@TODO` on cloudlet-vmId continuity during migration** — relevant since any evacuate-then-heal strategy leans on this exact path. Not investigated further this pass.

This strengthens rather than weakens the case for the "maximise service" design direction: since nothing is automatic or free, different healing strategies (migrate-all-then-heal vs. power-down-and-abandon vs. partial/priority evacuation) are genuine, independently meaningful policy choices, not thin wrappers around one obvious CloudSim mechanism. See 01-architecture.md, "Host Failure — 'Maximise Service' as a Fourth Goal, Reactivating Meta-Controller Selection," for the resulting architectural direction. ### Seed 49 Investigated as a Potential Outlier — Resolved: Assignment Luck, Not a Different Population (2026-07-20)

Seed 49's baseline makespan (2348.72) and total cost (0.5797) were roughly half of every other seed's — worth checking before trusting the aggregate rather than assuming it away.

**Reproduced exactly via `SelectorScenario.java` with `SEED = 49L`** — every RNG stream in that file derives from the single `SEED` constant via the same `SEED ^ 0x...` pattern copied into `SelectorMultiSim`, so this one-line change reproduces scenario_seed=49's population exactly. Confirmed: every printed cost/makespan/energy figure matched the CSV row to the printed decimal.

**Ruled out: an easier VM or host population.** The VM MIPS tier draw (four VMs at 1000, five at 500, three at 250) is close to an even split, not skewed toward fast VMs. Host #3 sitting completely empty doesn't explain the speed either — fewer active hosts means less aggregate capacity, which should mean *more* contention, not less; if anything this cuts against an "easier scenario" explanation.

**Root cause found in the t=100 VM allocation log's `remainingMI` column: VM#1 (1000 MIPS, the fastest tier) was carrying 1,269,767 MI across 7 cloudlets — by far the heaviest load of any VM in the run — while two VMs had zero cloudlets assigned.** `RANDOM_ASSIGNMENT` draws a VM id uniformly (`assignRng.nextInt(NUM_VMS)`), completely blind to that VM's MIPS tier. This seed's single heaviest workload chunk happened to land on the single fastest VM available — a favorable coincidence in the assignment draw, not a different or easier scenario.

**Generalizes to the whole sweep, not just this seed:** since cloudlet-to-VM assignment is MIPS-tier-blind by design, makespan is highly sensitive to whether any given seed's heaviest workload happens to land on a fast or slow VM — very likely the actual driver of makespan's SD (11.95%) being almost as large as its mean (12.19%) across the 10-scenario sweep, rather than genuine scenario-to-scenario population difficulty. See 07-limitations.md for the general form of this finding and the deliberate tension it sits in (uniform random assignment was chosen specifically for confound-free cross-controller-family fairness, 05-scenarios.md; a MIPS-aware assignment would reduce this variance but risks reintroducing exactly the kind of allocation-policy confound that decision was meant to avoid).

### Power Model Realism — Tier-Coupled to Real SPECpower Hardware Profiles (2026-07-27)

Refines, does not contradict, "Power Model Calibration" above — the static-power-dominant reasoning that motivated `PowerModelLinear(250, 0.6)` still holds; this replaces one uniform curve with three real ones, still calibrated the same way in spirit.

**Change: the single uniform `PowerModelLinear(250, 0.6)` applied to every host regardless of its already-existing hardware tier (Legacy/Standard/Modern, 05-scenarios.md "Host Parameter Heterogeneity") replaced with three real SPECpower_ssj2008-benchmarked profiles, indexed to that same tier roll.** `createDatacenter` now selects per-host from `POWER_MODEL_TIERS`, matching the tier index already used for `HOST_MIPS_TIERS`/`HOST_RAM_TIERS`/`HOST_BW_TIERS`:
- Legacy → `PowerModelSpecPowerHpProLiantMl110G3PentiumD930` — `{105, 112, 118, 125, 131, 137, 147, 153, 157, 164, 169}` W (0–100% utilization, 10% steps)
- Standard → `PowerModelSpecPowerHpProLiantMl110G5Xeon3075` — `{93.7, 97, 101, 105, 110, 116, 121, 125, 129, 133, 135}` W
- Modern → `PowerModelSpecPowerIbmX3550XeonX5675` — `{58.4, 98, 109, 118, 128, 140, 153, 170, 189, 205, 222}` W

All three are real SPEC-benchmarked profiles already shipped in `org.cloudbus.cloudsim.power.models`, not authored for this project. Empirical comparison run by the user (old uniform model vs. new tiered models, same scenario) came back with lower average power under the new profiles and no anomalies — consistent with the real hardware ranges these curves are drawn from, not re-verified against a separate ground truth beyond that plausibility check.

**Structural difference from `PowerModelLinear` that turned out to matter later (see "Host Power-State Control" below): none of the three `PowerModelSpecPower*` curves has a zero-utilization special case.** `PowerModelLinear.getPower()` has an explicit `if (utilization == 0) return 0` branch, independent of its formula — this is the entire mechanism behind this project's long-standing "empty host = 0W" ground-truth decision (see "Ground Truth: Empty Host = 0W," above). `PowerModelSpecPower` (the shared abstract base of all three profiles) has no equivalent — `getPower(0)` returns real measured idle wattage (`getPowerData(0)`, the first entry in each array above: 105W/93.7W/58.4W), not zero. Consequence: under the old model, "host has zero VMs" and "host is switched off" were accidentally identical (both 0W) — under the new model they are genuinely different physical states, which is what made the power-toggle actions below newly meaningful rather than redundant with existing consolidation-via-migration.

**Note for anyone re-running historical energy comparisons**: every energy/cost figure elsewhere in this file predates this change and was computed under the uniform `PowerModelLinear(250, 0.6)` model — not directly comparable to any future run made under the tiered SPECpower models without re-establishing a new baseline.

### Host Power-State Control — Verified, Built, and Made Physically Meaningful (2026-07-27)

Resolves the long-open "Direct host power-state control... unverified" candidate (01-architecture.md, "Additional Action-Type Candidates") and directly follows from the power-model-realism change above — the two were developed together, in the order: build → judge not worth keeping → reverse that judgement once the power model changed underneath it.

**Mechanism, confirmed via source before building anything.** `PowerHostEntity.setPowerModel(PowerModel)`/`getPowerModel()` exist directly on the interface (`org.cloudbus.cloudsim.core`), and `PowerHost.getPower()` reads through `getPowerModel().getPower(utilization)` — confirming a model swap correctly propagates to both direct `getPower()` reads and `PowerHostEntity.getEnergyLinearInterpolation`'s energy-accumulation calculation, with no changes needed to `PowerDatacenter`'s own per-cycle loop.

**`requestHostPowerDown(HostEntity)` / `requestHostPowerUp(HostEntity)` built as atomic, precondition-gated actions** — no bundled "evacuate then power down" mega-action (considered and rejected on the same combination-logic-invisible-to-typing grounds as the MIPS-scaling cascade, 01-architecture.md, 2026-07-13). Power-down requires the host already be empty (`getVmListForHost(host).size() == 0`) and not already down/booting; all draining is left to the LLM's own repeated `requestVmMigration` calls. Power-down fires effectively instantly (`send(getId(), 0, ...)`); power-up carries a real 100-unit delay via the same `schedule(getId(), delay, TAG, hostId)` self-event pattern already established for `HOST_REPAIR` — chosen because real shutdown is fast relative to boot, and by the time power-down is legal to call, the only real waiting (evacuation) already happened via migration's own bandwidth-based delay. State is swapped via `savedPowerModels` (a `Map<Integer, PowerModel>`): power-down saves the host's real model and installs a static `PowerModelOff` (flat 0W, a small new class); power-up restores the saved model when the delayed completion event fires (`processHostPowerUp`), not before.

**Reversed once, then reversed back — worth recording the actual reasoning, not just the conclusion.** First build judged these actions to add no real decision value: under `PowerModelLinear`'s zero-utilization special case, an idle-but-on host and a genuinely-off host both already read 0W, so a toggle between them changed nothing observable. Reconsidered directly: that "no value" verdict was entirely an artifact of the old model's own oversimplification, not a fact about the real world — idle-but-on and off are genuinely different physical states (a real idle server draws real, nonzero, measured power), and the SPECpower profiles above preserve exactly that distinction. Once the power model changed, the same toggle action became physically meaningful without any change to the action's own code. Lesson worth generalising: an action's apparent uselessness can be a property of the *model* it's tested against, not the action.

**Inrush/boot-power realism added, reusing the existing boot-delay window rather than new machinery.** Real hardware draws elevated power while booting (disk spin-up, POST, capacitor charging) — a genuine, well-documented phenomenon, though the literal millisecond-scale transient is well below this simulation's meaningful time resolution (cycles/cloudlet-runtimes on the order of tens of time units). Modelled instead as sustained elevated draw for the whole 100-unit boot window: `requestHostPowerUp` installs a `PowerModelSpike` decorator (wraps the host's real saved model, multiplies its output by `SPIKE_MULTIPLIER`) *synchronously*, at request time — not at completion — and `processHostPowerUp`'s existing restore-to-original logic naturally ends the spike when boot completes. No new `CloudActionTags`, no third scheduled event. **`SPIKE_MULTIPLIER = 1.2` is an unsourced placeholder**, not empirically grounded — real PSU inrush specs (2–10×) describe microsecond transients, not the sustained-draw abstraction used here; a defensible number for "extra components active during boot" was not researched, just estimated.

**Two real bugs caught and fixed during this build:**
- **Initial version routed the scheduled event to the wrong destination.** `send(host.getId(), delay, TAG)` sent the event to the *host's own ID* as if `Host` were an addressable `SimEntity` — it isn't (see "Architecture Decision: No New Interfaces Needed" above; `Host`/`VmScheduler`/providers are plain objects owned by the `Datacenter` entity). Fixed to `send(getId(), delay, TAG, hostId)` — Selector scheduling an event to itself, host id carried as payload — matching the exact shape already used for `HOST_REPAIR`/`CLOUDLET_INJECT`.
- **Duplicate in-flight power-up requests could NPE.** `isHostPoweredDown` stays `true` for the entire boot window (only cleared at completion), so it can't distinguish "off" from "currently booting" — a second `requestHostPowerUp` call during that window passed the existing guard and queued a second completion event. When the first event fired and correctly `savedPowerModels.remove(hostId)`'d the saved model, the second (redundant) firing later found nothing left to remove, got `null` back, and called `host.setPowerModel(null)` — a live NPE risk on the next `getPower()` call. Fixed with a second tracking set (`poweringUpHostIds`), a guard in `requestHostPowerUp` refusing a call while already booting, and a matching `isHostPoweringUp(HostEntity)` `ReadSpace` read so the LLM can observe the state rather than being silently refused with no explanation.

**Status: built, source-verified, bug-fixed, not yet run through a validation sweep.** Same caveat as the host-failure mechanism above — structurally sound, not yet empirically characterised (task `#10`).

### getPeDemand Removed From ReadSpace — Reversing the 2026-07-15 Promotion (2026-07-27)

**Reverses "VM PE-Count Deallocation — Built, Naming Finalised, Two `ReadSpace` Promotions" (2026-07-15, this file) and the corresponding 07-limitations.md entry — not a mistake being corrected, a sharper test replacing a too-broad one.** See 07-limitations.md, "The `ReadSpace`-promotion test from 2026-07-15... was too broad," for the full refined criterion. Short version: `getPeDemand` ("sum a VM's cloudlets' `getNumberOfPes()`") has exactly one correct answer, which was the entire justification for promoting it in the first place — but that test doesn't distinguish "worth protecting from the LLM" from "ordinary composition the LLM should be expected to do unprompted." Deriving it requires nothing hidden: both atomics it's built from (cloudlet exec-list access, per-cloudlet PE count) are already exposed. Framed explicitly as a deliberate research choice, not just a cleanup: leave the atomic tools in place, remove the pre-summed convenience method, and treat whether independently-generated modules reconstruct it correctly as a genuine (if low-stakes) generation-reliability data point, consistent with this project's actual research question.

**Three call sites depended on it, all found via a direct grep of the project files (not assumed absent from partial context) and fixed to inline the same sum:** `monitor_ETC.java` (reuses its already-fetched `execList` rather than re-fetching), `analyser_ETC3.java`, `analyser_ETC4.java` (the latter needed a new `import org.cloudbus.cloudsim.Cloudlet;`, since it previously only reached cloudlets indirectly through the now-removed method). All three verified correct against the existing pattern already used in `Selector.getVmEffectiveThroughput` and `analyser_ETC3`'s own pre-existing `targetPeDemand` logging loop — same shape, no new formula introduced. `getVmEffectiveThroughput` itself was never a caller (it already inlined its own copy independently) and needed no change.

**Status: both `ReadSpace`/`Selector.java` and all three dependent files updated and consistent.** Not yet re-run through the PE-allocation/deallocation validation sweep (04-family-power.md, "VM Core Count — First Validated Runs") to confirm behaviour is unchanged post-removal — low risk given the replacement is an exact algebraic match, but not independently re-verified by a run.
